用户再次明确要求“你来进行发布”。本次按 AGENTS.md 2026-10-29 的“备份与发布分离、数据库/任务合同变化人工选定方案”执行。此方案调整此前重构计划的发布前全库备份选择，不改变两份事实、财务完整性和旧表保留要求。不把该授权写成用户明确豁免测试或恢复验证；实际未执行项逐项记录。

## 本次选择

- 使用已通过最终审查及变更范围验证的精确源码和镜像；既有全量门禁失败保留记录，采用人工发布，不伪造全量通过缓存。
- **本轮不创建新全库备份、不执行新恢复演练、不扩容备份盘、不删除已有备份。**旧镜像摘要、源码版本和实际配置保持可追溯，私有发布状态按原工具保留。原备份不能宣称覆盖当前全部数据。
- 先停止 API、唯一 Beat，取消九个 Worker 消费，等待在途及预留任务正常结束并连续两次空闲，再降至零 Pod。保留消息、任务 ID、UNKNOWN 保护，不清队列。
- 原 Secret、四个开关、配额、并发、资源、更新策略、数据库池和退出宽限保持；全部 Deployment spec 只改镜像。

## 两个发布阶段

1. 第一阶段：`0110_campaign_copy → 0113_creative_material`。只新增创意身份、创意事实和独立影子投影及对应索引/触发器；旧素材页面及旧任务继续运行，不删除或改写已有业务事实。
2. 本地身份回填、成对创意/广告回补和逐指标对账。近完整日优先，保留 NULL、未知和有符号差额；规则仅试算，不启用或执行广告操作。
3. 第二阶段：`0113_creative_material → 0114_retire_material`。新增有效脏桶索引；退休精确的旧报表任务、需求和未发布消息，保留原事实、历史任务审计及成本未知证据；页面/规则切换新源。不删除三张旧表或 `creative_ids` 列。
4. 切换稳定至少七天后的物理删表/列是独立后续操作，必须重新审查引用、备份与可恢复性，本轮不执行。

## 切换与失败处理

- 使用共享发布锁，协调本项目 Jenkins。先让候选辅助 Pod 就绪并只读核对旧 head，再冻结写入、正常排空，指定 Alembic head 迁移；不重放结果不明的迁移调用。
- 所有应用保持零副本直到迁移结果确认；仅更新精确镜像后，先九个 Worker，后 API，最后唯一 Beat。核对任务注册、11 角色 Ready、摘要、实际配置/开关和 HTTPS。
- 迁移前失败可按原模板恢复。迁移开始后的异常保留锁和现场，先核对进程、数据库 head 和兼容性，再继续候选或制定恢复方案；不自动降数据库或盲目启动旧代码。
- 不以基础健康代替报表业务验收。第二阶段前后检查财务对账、停用规则试算、新旧任务行为与真实积压；旧通用定向目录任务的来源不明时不批量猜测取消。

压缩体积预检曾在应用不停服时启动，随后因本次选择不创建新备份而主动停止。只读流未保存，临时客户端与锁已删除；部分流量不是完整备份大小，也不是恢复证明。此前 126.6 GiB 是物理库除以四得到的估算门槛，不能称为本次实际备份体积。
