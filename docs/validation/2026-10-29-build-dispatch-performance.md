# 搭建封面与投递调度优化

## 已证实的问题

生产 WQUV 在推进但效率异常：素材完成后广告仍等待封面；控制队列积压时业务队列为空，消息投递 tick 已排队过期。控制日志中的报表昨日收尾查询触发25秒软超时，另见素材核验死锁；后两项原因仍需分别排查，不能声称本次已经消除。

真实 PostgreSQL/Redis 回归重现：2素材×2账户的空封面探测在无结果可发布时仍执行64条发布SQL；向10账户共享时，逐账户鉴权会重复完整业务核验11次，加上准入前后共13次。

## 本次变更

- 空探测不再进入结果发布的素材锁和整批校验；分页保存、批次范围及成员租约检查保持。
- SDK与MCP共享目标逐账户权限验证保持；完整业务围栏仍在物理请求准入前后重新执行，10账户由13次降为2次，不缓存跨请求权限。
- `jobs.flush_dispatch`及每秒Beat投递从`control`改到已有`builds`池，避免受报表规划、修复阻塞。短投递使用优先级0、搭建业务使用3，防止搭建队列积压再次饿死投递。任务名、参数、持久outbox、租户公平和消息幂等不变；既有control消息仍可消费。没有新增Worker、并发、配额或数据库结构。
- 每个封面共享切片记录`cover_share_slice`结构化日志：租户、BC、job/batch/dispatch/revision、阶段、业务结果、错误码、核验次数/耗时及总耗时；不输出请求正文、凭据或素材URL。可用job/batch关联持久任务，再关联搭建素材。尚不是集中日志平台或完整端到端追踪。

## 选定发布方案

目标为阿里云生产ACK的test命名空间、tkada.shortclipflix.com；基线72e3282c9d88a5a9a7292801dbd316c35e8c31b2，schema0045。这是既有任务的消费队列调整：新旧版本均注册同名任务，队列均已存在，滚动更新无需改历史消息或清空队列；回退只恢复镜像，已在builds的消息仍可由旧版本消费。仅发布本次已提交文件，不包含工作区其他维护/前端改动。

按2026-10-27/29授权执行范围明确、无DDL的快速更新：不备份、不恢复演练、不额外等待全量队列排空；保留精确镜像、发布锁、配置不变核对和正常退出宽限。构建前后核对11角色与单Beat；上线后核验实际路由、封面日志、任务进展和最老待投递时间。builds池仍可能被长创建请求占满，需观察其队列延迟；本次不是专属调度Worker。
