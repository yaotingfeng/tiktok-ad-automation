# 连山 RDS 官方源表与 TK-ADA 数据库设计对照

## 结论与证据边界

数据库设计属于整体改造范围，不能将目前问题全部归于平台额度或机器配置。TK-ADA 已有类型化日事实、业务唯一键、月分区及部分汇总；缺口主要是在线读取仍承担宽目录、历史关联、展示身份归并，以及控制流水的工作集治理。不是“所有表都错了”，也不是“数据库设计已无问题”。

本轮补查的是巨量项目保存的**官方 RDS 源表结构盘点**，不是只看应用本地 PostgreSQL 表。来源为参考仓库 `ad_automation` 的 `docs/superpowers/specs/2026-07-18-lianshan-rds-schema.md`，记录 2026-07-18 直连生产 MySQL 只读复核；抽取代码为 `backend/app/integrations/lianshan_rds.py`。参考源码基线 `8b2e9ee1b`，TK-ADA 代码基线 `12d24fa3`。本轮未重新连接连山 RDS，不能保证该历史快照等于今天的所有订阅结构；也不能把订阅交付表当作平台全部内部数据库架构。

TK-ADA 生产规模及 EXPLAIN 证据沿用[前轮对照](2026-10-31-oceanengine-comparison.md)，属于 `0642ad3d` 上线期间，不是之后 `12d24fa3` 的性能结果。本轮没有运行应用、迁移或生产写入。

## 官方源表实际如何组织

| 源表族（省略日期后缀） | 承载内容 | 历史快照列数 | 主要业务索引前缀（不含租户） |
| --- | --- | ---: | --- |
| `lianshan_report_std` | 升级版账户/项目/营销报表，同表携带三级 ID | 174 | 账户/营销/统计时间/app_code；账户/项目/统计时间；账户/统计时间 |
| `lianshan_material_std` | 升级版素材报表 | 143 | 账户/素材/统计时间/app_code；账户/项目/统计时间；账户/营销/统计时间 |
| `lianshan_report_uni` | 全域账户/项目报表 | 80 | 账户/项目/统计时间；账户/统计时间 |
| `lianshan_material_uni` | 全域素材报表，无项目列 | 53 | 账户/image_mode/统计时间；账户/素材/统计时间；账户/统计时间 |

共同特征：

- 每订阅任务独立库，按日物理表，当天与次日预建。不是每个账户一张表，也不是把每个广告层级都独立成表。
- `id BIGINT UNSIGNED` 为主键，另有 `(uid,stat_time)` 索引。盘点中的业务索引不构成已验证的自然唯一约束；不能据此断言“账户＋对象＋时间”已覆盖所有维度。
- `update_time DATETIME` 有**单列** `idx_update_time`；消费端按 `(update_time,id)` 排序和续读，解决同一更新时间多行的边界。复合游标不等于源表声明了复合索引，也不能单独解决所有迟到更新，仍须重叠回扫与对账。
- 统计时点 `stat_time/stat_time_hour` 与创建、更新时间分列；账户、项目、素材和指标都是类型化列。
- 升级版两表没有原生 `op/op_ts/identifier`，由应用抽取器合成，不应误认为额外平台变更日志协议。
- 升级版消耗原始单位与全域指标单位不同；源中存在 DOUBLE/浮点指标。TK-ADA 应保留自身金额精度和币种合同，不能照搬字段类型或单位。

RDS 已提供可直接查询的变更时间，这是减少重复读取的重要来源优势。TK-ADA 本地新增一个 `updated_at` 并不会让 TikTok 分页接口自动成为同样的远端增量源。

## 对照后必须保留、改造和核实的部分

| 项目 | TK-ADA 证据 | 判断与决定 |
| --- | --- | --- |
| 事实按粒度存储 | `reporting/store_models.py`：广告日、素材日、系列日/小时分开；金额 Numeric，平台缺失值为 NULL | 已有合理基础，保留；不重建第二套同义事实库 |
| 时间切分 | `reporting/partitions.py`：广告日、素材日按月分区 | 不能称为所有报表堆在一张未分区表；按实际月分区大小比较日/月，不因官方按日就直接迁移 |
| 目录宽字段 | `ads/models.py:AdObject.configuration` 为 JSONB；`reporting/row_set.py:_obj_select` 将其带入候选集合 | 新增窄的类型化在线投影；完整 JSON 留详情。统一目录表本身不是已证实根因，先消除读取成本，再决定是否物理拆表 |
| 最新身份与历史 | `campaign_name_projection` 保存修订；`row_set.py:_proj_cte` 对候选取最新；素材引用保存历史位置 | 单独维护当前命名/使用关系投影，保留历史核算证据；不以删除历史代替优化 |
| 素材页关联范围 | `material_query.py:materialize_material_rows` 先对全部授权账户和日期调用 `post_video_map`，随后才约束页内身份 | 增加可反查的索引和素材展示日模型，页内补详情；不是给原查询加 LIMIT 就解决 |
| 汇总层 | 已有 `campaign_report_day`，广告组和素材展示身份仍需要更多查询时归并 | 复用系列汇总，增量维护广告组/素材展示日模型，只重算受影响桶；汇总不独立多拉一次平台 |
| 控制与临时数据 | 前轮元数据记录大量投递流水、目录运行和页正文 | 活跃调度头与终态历史分工，暂存有发布证据后有界回收；总行数不等于待执行积压或 MVCC 膨胀 |
| 发布期分区 DDL | `ensure_month_partitions_for_range` 在缺分区时显式取得父表 `ACCESS EXCLUSIVE` 锁并搬 DEFAULT 行 | 已知条件性阻塞风险，分区预建移出发布热路径；无当前锁采样不能称其为现在持续锁库的根因 |

## DDL 前必须补齐的物理设计审计

以下纳入总体方案 W0/W1，不是本轮已经完成的迁移或实测。

1. **逐表确认一行代表什么。** 输出“官方响应维度 → 事实自然身份 → 数据库唯一约束 → 展示身份”矩阵。`MaterialReportDay` 当前主键不含 `main_material_type`，`MaterialPostLink` 同样将类型作为普通列；而关联查询已经按 ID＋类型区分。这是必须核验的合同疑点，尚无证据证明发生了跨类型覆盖。先确认平台是否保证跨类型 ID 唯一、类型是否会被纠正；若为身份组成部分，再同时修改事实、链接、发布去重与汇总。不能直接追加类型主键，导致类型纠正后新旧两行重复计费。
2. **按查询形状定索引。** 同时覆盖单账户同步/发布、跨账户报表和本页素材反查。现有日事实已存在账户前导主键与日期前导索引；先核对实际 DDL，再比较不同前导列的 buffers、排序/溢写和写放大，不重复建已有索引。租户与授权限制不得因模仿源表而消失。
3. **明确时间与版本。** 平台业务日期、源更新时间（仅平台实际提供时）、本地观测时间、发布版本分别定义。`fetched_at` 不当作源变更水位；当前投影和日汇总须能防旧覆盖、处理迟到纠正、回填后追平。
4. **量化分区方案。** 记录每个分区的行数、heap/index/TOAST、日增量与热点分布；对 1/7/31/90 日及最大账户日，在相同数据上比较当前月分区与候选日分区的读、写、规划和维护成本。若选择更细分区，W1 前修改规格并给出迁移计划；不按 BC 复制金额事实，不默认一租户一库。
5. **验证列宽与精度。** 热查询只携带需要的列；ID 是否可缩短、计数 Numeric 是否可改 BIGINT，必须先验官方合同、范围和迁移收益。金额精度、币种、当地日及 NULL/0 不变；源表很宽不代表在线查询应读取所有列。
6. **回填和增长一起验收。** 新旧读模型逐桶核对金额、行数、身份与权限，覆盖跨账户、图片/视频、类型纠正和历史补链。估算双份数据、索引构建、WAL 峰值；记录新增/回收字节和清理最老年龄。事实量扩大与无关历史扩大分别测量，不能只测空库或几十行。

索引和分区的决定以实际访问模式为依据：[PostgreSQL 多列索引文档](https://www.postgresql.org/docs/current/indexes-multicolumn.html)说明前导列条件影响扫描范围；[分区文档](https://www.postgresql.org/docs/current/ddl-partitioning.html)说明裁剪收益及分区数量带来的规划/维护取舍。本方案不依赖尚未核验服务器版本的新优化器能力。

## 收敛到整体方案的决定

保留 PG、已有规范事实和必要历史；明确新增在线窄投影/必要日模型、活跃调度工作集与暂存生命周期。官方 RDS 对照用于确定数据组织、增量和索引方法，不能作为照抄源库、取消租户隔离或承诺相同吞吐的依据。

进入实现的门槛是：上述粒度矩阵、实际索引清单、分区/空间决策和代表性基线齐备。最终仍须通过[整体规格](../superpowers/specs/2026-10-31-sync-query-redesign.md)的混合负载、金额一致性和稳定消化积压验收；增加表或索引本身不等于问题解决。
