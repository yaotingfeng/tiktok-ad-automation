## 人工选定的无备份迁移方案

依据AGENTS 2026-10-29规则及部署手册“人工不备份迁移方案”，本次明确不创建备份、不做恢复演练；不伪造备份证明。普通deploy自动拒绝数据合同变化是停服前门禁，本次在已有全量发布授权下先完成审查并人工选择以下具体方案。

1. 暂停本项目Jenkins且确认无active/queued构建，取得项目发布锁。冻结精确旧/新SHA与镜像digest，私有保存原Deployment UID/spec与配置基线，保留未知结果不重放。
2. 推送origin/main及公司main，构建精确候选AMD64镜像并确认revision/digest，候选就绪后才停止生产。
3. 停API/Beat，取消9个Worker消费并正常排空，连续两次无active/reserved/scheduled；停止Worker、确认所有旧Pod退出、broker无未确认投递。保留队列和UNKNOWN，不清理业务消息。复用creative-unit-drain守卫，迁移前查无应用残留写事务/其它迁移。
4. 同实际Secret/配置启动本项目单次migration Job，backoffLimit=0；整链`0101→0102→0103→0105→0106→0104`事务升级。按实际规模给Job两小时外层上限、单语句45分钟、锁等待15秒；不调整服务器全局参数或扩容，不自动重试未知迁移。JIT仅此迁移会话关闭。冻结期间滚动记录阶段与异常。
5. 成功确认0104后，针对新增读表/分区、成员头及证据表ANALYZE，补上首次查询统计。然后在全部角色零副本时CAS更新同一候选镜像，完整spec仅镜像变化，API和Worker先启动，唯一Beat最后启动。
6. 回读11角色Ready、真实imageID、实际配置/四开关/数据库池、HTTPS与schema，并观察真实报表和同步；基础健康不能代替平台OAuth/广告创建/赔付到账。
7. 迁移开始后不自动切旧程序或降级数据库。失败时保留锁、Job与日志，先确认PG是否回滚及head；0106新快照格式成功生效后只做候选前向修复。完成后解除发布锁，恢复原Jenkins状态，提交并推送实际结果。
