# 目标视频推送后提前准备封面

## 范围与原因

用户要求继续优化搭建，并沿用此前测试后推送、发布生产的授权。生产基线为 `48123e1c` / `0062_directory_pending_index`，本地 main 另含尚未发布的图片轮播合同，因此本次在私有独立检出使用已有 `feat/automation-rules-ux` 分支，仅发布本修复与既有发布记录，不包含 main 的轮播迁移。控制慢查询和容量已由同步专项继续优化，本轮不重复修改或宣称解决全部后台积压。

源上传已有成功后启动封面的事件；目标视频分发的单条和批量核实成功路径此前都未登记目标封面事件，只能等搭建素材步骤或广告首次检查时准备。回归先真实复现：目标视频已经 ready，目标封面事件仍不存在。

## 改动

- 单条目标上传、详情核实及批量共享核实发布真实 VID 时，在同一事务登记目标封面启动事件；事件不进行网络操作，视频成功与事件不会分开丢失。
- 复用 `materials.prepare_source_cover` 已有 control 消费者。源事件 payload 不变；新目标事件额外带 `purpose=BUILD`，使用 `target-cover:<operation_id>` 独立业务键及确认字段。目标沿现有 BUILD 封面共享逻辑执行，复用当前已验证图片及已有封面任务，不改为每账户强制上传图片。
- 消费核验租户、操作者、持久事件、冻结路线和真实目标 VID；旧 VID/连接事件不启动新视频封面。重复消息幂等，确认与封面任务同事务提交；同 VID 暂时重新核实则不提前确认启动完成。
- 原每分钟修复器覆盖新目标事件；先筛已登记但未确认的目标操作，避免每轮给全部历史共享操作做 outbox 探测。增加 `cover_start_prepared` 日志，记录准备结论、具体任务和失败码；不把事务内准备日志当作已完成图片上传。
- 不创建广告，不批量补发历史 UNKNOWN，不追溯启动全部旧视频封面；新成功推送提前准备，历史素材仍由现有搭建兜底。视频 ready 仍表示视频成功，封面有自己的独立状态。

## 测试与查询证据

真实独立 PostgreSQL/Redis；外部 TikTok HTTP 使用替身，没有真实平台上传。目标缺事件先失败；源/目标事件首轮11项通过。分发、并发、原生共享、URL转存、原件导入及搭建封面组合228项通过（364.49秒）。最后发现并回归了“同VID重新核实时误确认启动完成”的边界，修正后的源/目标事件及URL导入专项60项通过（34.51秒），包含真实Celery参数消费边界。修改文件Ruff、ty及差异检查通过。

生产仅用 READ ONLY 和4秒SQL期限执行 SELECT 的 EXPLAIN ANALYZE，移除 FOR UPDATE，没有补派/写入生产任务。初稿空结果查询1885.309ms、303311次shared hits；增加目标已登记/未确认筛选后119.893ms、167227次shared hits。两次缓存条件不同，不能据此承诺固定提速倍数；候选仍使用 `(tenant_id,task_key)` 唯一索引，源事件沿已有核查范围。

## 发布选择与回退边界

无DDL、新队列、新Worker、开关或并发/配额调整；保留11角色及control3、后台4的现有部署模板。新增的是已审查的任务payload变体及操作JSON元数据，因此不走忽略任务合同检查的默认发布；使用已审查的精确分支发布驱动，正常grace停旧消费者后统一切换。按用户既有授权不新建备份、不做恢复演练、不额外等待全部历史积压清空，保留独占锁、配置哈希、镜像摘要、schema和完整部署模板核对。

旧程序不认识新目标payload，不能在有未完成目标启动事件时直接回退旧消费者；应保持候选修复前进，或先经候选处理新事件并审查其余封面任务再制定回退。不删除新事件或改写其已确认状态。源历史payload完全保持。

生产正式结果和下一批真实推送吞吐分别记录；不能将回归通过或服务Ready写成下一整批搭建速度已验收。
