# 2026-10-30 同步积压：素材类型与完成条件的根因核验

本轮只诊断、复现和记录，没有修改生产配置、业务数据或应用代码。生产仍为 `68c5fedbe65c4c03f6b818c72519dfaddfc20641`，采集五类 Worker 均 Ready、重启 0。此前广告明细在途 6→12 的调整已经上线，但不能以接口调用增加证明整体积压解决。

## 主要新发现：轮播图被要求补视频 VID

18:19:16–18:19:22，北京时间，对 xuyin 全部 4,859 个归属账户分批只读统计，范围为账户当地今天、有消耗的主素材；每批限时 4 秒、锁等待 300ms，全部完成。批间正常生产仍写入，数字不是全库同一事务快照。

| CAROUSEL_SPARK_ADS → CAROUSEL_SPARK_ADS → 未解析 | 34,978 |

共 35,551 个未解析主素材，其中 35,523 个为轮播图、28 个为视频。轮播图占 99.92%。这说明此前将约 3.5 万个缺口笼统描述为“未关联视频/帖子等待目录”掩盖了素材类型差异；不代表 99.92% 的全部同步任务或 API 请求都无效。

生产代码的完整因果链：

1. `reporting/health.py::measure_coverage` 对所有有消耗的主素材检查 `material_post_link.platform_material_id IS NOT NULL`，没有按视频/轮播类型区分；不满足便计入 `unlinked_material_posts` 并产生 links 修复需求。
2. `material_links.py::needs_material_links` 与 `missing_video_ids` 同样把全部有价值主素材送入视频映射完成条件。任务内的广告归属扫描结束，不等于此条件满足。
3. `material_identity.py::pending_asset_ids` 只接受 `VIDEO_NON_SPARK_ADS`；`spark_identity.py::pending_spark_links` 只接受 `VIDEO_SPARK_ADS`。轮播图不会进入任一视频解析路径。
4. 生产 `_resolve_videos` 要求一个广告内素材 ID 唯一对应一个平台素材 ID。一个正确的多图轮播可以有多个 IMAGE 引用；不能任选其中一张作为整组视频 VID。
5. `wait_for_dependencies` 对此保留 `material_directory_pending`，`request_link_directory` 的“完整目录无需再读”排除条件又只覆盖特定 Spark 视频。因此已有广告和图片证据的轮播仍可继续要求目录补读。去重/退避限制频率，但不能让不适用的完成条件变成可满足。

这是一条已证实的业务完成条件错误，解释了主要素材告警为什么不能靠升配、调并发或加快 SQL 消除。它不是 TikTok 返回 40100 的同义词，也不能解释全部历史财务任务。

## 使用精确生产代码的最小复现

加载本机精确生产候选 `68c5fed...`，连接独立本地 PostgreSQL 测试库，在回滚事务中构造：

- 有消耗的 `CAROUSEL_SPARK_ADS` 事实；

- 正确的轮播广告配置和两条 complete 的 IMAGE 引用；
- 不存在且不应制造的视频 VID。

连续执行三个解析/完成检查轮次，结果完全相同：两条视频解析路径均返回 False；归属扫描返回完成；`needs_material_links=True`；任务继续 `WAITING/material_directory_pending`；视频调用为零。复现没有真实 TikTok 调用、没有生产写入，测试数据全部回滚。

此外，回查 17:47–17:57 日志中按累计耗时选出的 20 个素材关联任务，20 个范围均含轮播图，其中 6 个仅含轮播图；这是偏向耗时任务的定向样本，不代表所有任务随机分布。

## 被排除的中间假设

最初从“已有广告内素材 ID 但无法对应 VID”怀疑旧桥接 ID 失效。视频条件下确有小缺陷：同一内容证据，空 bridge 能解析；非空失效 bridge 被备用解析候选过滤，三轮无调用并继续等待。但进一步生产分类只有 2 条满足该特定 Spark 视频条件，不能把它当作 2.1 万条异常的主因。最终按实际类型拆分才发现绝大多数为轮播图。

还按当前最老/最新各 32 个实时素材子运行核对冻结父观察与当前对象，没有发现全体或部分父对象已被较新观察覆盖。样本可能重叠，不外推全量；不支持“所有子任务都反复被新父任务作废”的猜测，没有取消这些任务。

## 目录与历史任务是另外两类问题

18:05 全部 4,859 个归属账户同口径拆分：16,061 条当日有消耗广告中，2,156 条三层目录均新鲜，13,905 条至少一层过期；对象本体缺失为 0。此健康字段实际上包括过期，不能把它叫作 13,905 个完全未同步的广告。

17:47–17:57 的十分钟日志显示：

- 实时目录 12 槽墙钟占用约 99.62%；记录到 HTTP 响应耗时累计约 4,588.8 秒，占任务累计时长约 64%。剩余时间含数据库、本地发布/解析及调度，不能全部归为数据库或锁。
- 后台 4 槽约 99.79%；目录步骤占累计任务时长约 61.3%，历史报表/关联占约 38.7%。这些工作实际共用消费者。
- 实时报表 12 槽平均约 48.53%，但其队列不自动承接后台任务。静态分池造成后台饱和时其他池仍可空闲；不能用某瞬间 12/12 活跃说明整个窗口没有闲置。
- 实时报表素材关联 2,207 步仅 3 个 COMPLETE，后台关联 346 步仅 5 个 COMPLETE；步骤可能有部分有效进展，不能将其余全部称作无效请求。
- 两个报表消费者合计 872 次发送前 endpoint_rate 拒绝、52 次真实 40100。二者同时存在；本地拒绝不算平台请求。

18:00:24 固定的 39,112 个目录任务，18:05:01 回读全部身份：旧任务中 1,267 个真实 COMPLETE 且有 published_version，17 个 STALE；其中后台真实完成 106 个、实时 1,161 个。说明系统确实在交付，并非全部空转；但是后台有效消化明显慢，短窗口不外推清空时间。

这些证据支持：当前重点是错误的素材完成目标、目录刷新负载与后台容量分配。没有证据证明继续增加数据库内存能修正轮播图的视频完成条件。

## 后续修复必须覆盖的边界

视频、轮播及其他素材需要适用各自身份的完成判定。对轮播不能制造视频 VID，也不能仅改告警计数；要同时修正任务产生、任务完成、依赖补读、历史等待任务自然退出或转入正确的轮播归属校验，以及健康指标。保留真实广告归属、轮播图片集合/帖子身份和全部金额，不删除未完成财务任务、不用减少显示数字冒充补齐。

主线虽已有未上线的轮播展示/身份相关改动，但当前 health 和链接任务仍使用未限定类型的完成检查；不能简单声称“主线已有功能，发布即可全部解决”，也不能混入未审查主线迁移。

本轮没有发布新修复。验收必须查看按类型拆分的实际缺口、无用目录补读/关联请求是否下降，以及正常新业务下真实旧任务完成量；不能只验收 Worker Ready 或测试数量。
