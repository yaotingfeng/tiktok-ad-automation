## 原因和实现

- 服务器原件已完整保存并校验，但固定的五项未知服务能力在选账户前阻断；平台上传尝试为零。完整目录中的账户角色为 ADMIN，旧观察逻辑仍固定发布未知上传 scope。
- 按用户本次要求，以实际执行和回读替代原五项静态服务保证。工程容量与已接入合同版本继续受限；MCP 请求关闭自动修复和绑定，客户端不重放未知请求。原件 MD5、大小、VID 必须由真实回读匹配才能入库成功；结果未知保留原件及来源槽位，只回查。
- 实际 token 的 `mcp:tt4b` scope 与已验证主体允许申请素材操作；账户仍需同租户/BC/连接完整授权交集、可操作状态及 ADMIN/OPERATOR 角色。ANALYST、未知角色和失权不允许上传。搭建权限仍按原独立规则，不由上传权限推断。
- 显式能力重检会刷新旧版本的未知上传事实，保留授权和 BC 绑定代数，无需重新 OAuth。正常上传继续使用原来源池；运维恢复可显式指定已授权账户，满载或失权不得换到其他账户。
- 修正远端完整文件名的 100 字节工程边界：先预留唯一追踪后缀长度，再截取原名，避免原名合法但拼接后超长。

本次决策替代早期设计/验收文档中“必须证明服务内部五项能力才允许 MCP URL 上传”的要求，不将未知服务行为伪装为已验证。此前测试中的 SYNTHETIC 记录仍只用于离线测试。
