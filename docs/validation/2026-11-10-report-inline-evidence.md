# 素材快照版本内联与保留期

## 原因与方案

同一4859账户、7日范围冻结约15.5万行、18.1万条版本关联。生产证据历史约3800万行、30 GB。逐条外键检查及批量父行锁定都需要大量随机回表；批量预取单阶段仍达117秒，不能作为修复交付。

快照行直接保存不可变版本UUID数组，分页/选择/导出仍按原版本展开并验证租户、账户、VID和成员数。当前目录的版本外键、证据不可变触发器保持。旧关联表只为迁移前尚未过期的快照保留，不参与新快照读取或写入。

历史清理仍至少保留退休1小时的版本，并额外保留最早有效快照事务开始之后退休的全部版本；快照created_at使用数据库transaction_timestamp，避免构建过程中的同步退休落在保护边界之外。构建取得共享事务级保留锁，清理尝试独占锁，存在构建时跳过本轮，不阻塞构建等待长清理。这样提交前由锁保护、提交后由有效快照时间水位保护；不依赖应用与数据库时钟一致。

迁移0109为快照行增加UUID数组、搬移旧关联，并增加帖子优先的批量关联覆盖索引、期间状态及投影水位覆盖索引，不改广告或经营事实。帖子按所选事实的帖子ID批量读取，关联后再次约束授权账户与素材类型；同一期间状态只读一次供覆盖和缺失日期共用。集合聚合仅在保存点内使用16MiB工作区，成功或失败后恢复原连接设置。降级恢复关联外键，不能在旧证据已经被合法清理之后强行降级历史过期快照；降级先删除过期快照。

## 实施与验证

1. 增加内联列和数据迁移；删除未通过验证的分批父版本预取实现。
2. 快照写入、页内解析和证据清理统一使用保留合同。
3. 真实PostgreSQL验证原版本冻结、缺失/越权失败、清理水位、构建与清理互斥、迁移往返。
4. 内存受限探针在临时快照行表中验证候选，不修改生产持久结构。通过后沿用授权目标、共享发布锁和CI协调，正常停写排空，单事务0108→0109，精确镜像恢复；不执行备份或恢复演练。上线后再实测六维。

真实PostgreSQL与独立Redis测试库针对性回归82项通过，包括5项内联生命周期测试；历史证据迁移2项另行通过（含旧数据升级到当前解析器、逐值降级往返），合计84项不同测试。7个实现文件Mypy、变更Python文件Ruff、格式和编译检查通过。临时快照行表的首个候选完整素材链路为53.624秒（快照42.827秒、首50条10.796秒），已经可返回但仍慢；该样本尚未包含最后两个覆盖索引和期间复用，不能当作最终验收。生产迁移和六维实测待补齐。
