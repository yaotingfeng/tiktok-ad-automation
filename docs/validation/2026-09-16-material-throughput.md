# 素材集中上传与封面批量共享

用户批准集中源账户、去除人为单文件串行、上传后提前准备封面并按真实平台合同批量共享；不保留失败重传或新旧兼容分支。仅新加坡测试服在发布范围，生产不变。本文的本地测试均使用真实 PostgreSQL/Redis，外部 SDK/MCP 在 HTTP 传输边界使用替身，不能冒充真实平台端到端吞吐验收。

## 行为与合同

- 新素材在租户/BC 首次合法选择时固定主素材账户，取消不同文件之间单账户在途一项门槛。短数据库锁只保护首次选择与账本，不跨网络。历史实际来源、同文件幂等、真实撤权和 UNKNOWN 围栏保留；失效不自动切换账户。
- 视频上传成功与源封面 outbox 在同一事务写入；封面 HTTP 异步执行，图片失败不将已成功的视频改为失败。延迟旧 VID 事件不能替换新资产；任务接收确认与封面创建同事务。
- SOURCE 上传封面后回读真实图片 MID。BUILD 复用已核实目标图片，否则按真实来源共享 IMAGE；VIDEO 与 IMAGE 分别发送，不将 image_id 冒充 material_id，不假设目标 ID 等于源 ID。
- 同源最多 20 MID × 10 目标；现有待处理项立即组批，不为填满而等待。每轮只读一个目标库存页，游标、已核实目标、唯一批次唤醒和 outbox 原子持久化，避免慢接口超过任务期限后反复从第一页扫描。
- 已发送 IMAGE 请求不重发、不切换目标上传。明确拒绝的目标/MID 保留 BLOCKED；不明确的结果保持 UNKNOWN 并只读核实。VIDEO 的逐目标 `failed_infos` 也保留在不可变回执中，不再误将业务部分失败当全部成功。
- 源位置由真实成功上传账本确认，包含原上传账户自身及真实 URL relay 上传。响应丢失后已严格核实的 URL 上传使用独立 `verified_upload_video_id`，不伪造原上传响应；native_share 派生副本不能冒充源所有者。

官方依据：[共享创意素材](https://business-api.tiktok.com/portal/docs/share-creative-assets/v1.3)、[图片详情](https://business-api.tiktok.com/portal/docs/get-info-about-images/v1.3)、[图片搜索](https://business-api.tiktok.com/portal/docs?id=1740052016789506)。共享上限和图片 MID/目标实际 ID 分别由合同测试验证，不将本地 QPS 配置说成官方账户额度。

## 资源与发布边界

迁移链：`preview_display_drama_id → material_primary_account → material_cover_sharing → material_share_receipts`。历史主账户/MID/共享回执不伪造回填；旧封面初始 BUILD，新 IMAGE 批次为空。发布前必须全备份、隔离恢复演练，并对来源、上传操作、分发、批次、响应归档和 outbox 做迁移前后摘要比较。
