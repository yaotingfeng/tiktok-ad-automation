用户要求先解决发布耗时，目标为触发发布到生产服务就绪不超过五分钟。本轮只处理发布，不继续扩展同步清欠。

备份目前为单连接 `pg_dump`，此前读写分离代理的并行快照/锁问题导致失败，不能仅把 jobs 改大就宣称解决。恢复已经使用四进程，仍需十分钟。仅缓存构建或增加检查并发无法消除这个主要耗时。

## 已确认的备份要求调整

用户已明确要求“你处理一下”，确认普通发布与备份分离。AGENTS.md、deployment.md和生产手册已同步新规则：

- 普通且无数据库迁移、持久化数据格式/任务合同变化的发布，可使用已核验的近期数据库备份；每次仍保存旧版程序、配置及 Redis 状态。该方式没有发布瞬间的独立数据库全备，不能把旧 PG 备份与当前 Redis 快照称为同一时点的一致恢复包。
- 完整备份及隔离恢复独立运行；涉及上述数据变化的发布继续原完整流程。独立备份不能沿用现有 `backup` 命令直接定时执行而不说明影响，因为现有命令会停止服务。
- 上线前必须核实实际备份时间、恢复范围和独立备份执行方式。现有生产文档曾注明托管自动备份策略未经云控制台核实；不能把 README 中“已有托管策略”当成验证证据。
- 普通小改动以端到端五分钟实测验收；需要十多分钟的完整回归或长任务排空时如实报告例外，不强杀在途任务、不改起算点冒充达标。

实现复用原发布器：普通发布核验24小时内完整备份和恢复证据，保留程序/配置/Redis归档后仅切镜像；敏感路径或显式 FULL_BACKUP 继续完整流程。Jenkins每天北京时间04时段执行独立在线数据库备份和完整恢复验证，比每周恢复演练更频繁；应用全程不停服，不挂载在线Beat盘，不把在线PG与瞬时Redis拼成一致快照。不依赖尚未核实的云托管备份。

## 已完成的可独立改动

`deploy/local.py` 从已有发布状态历史输出各阶段耗时到 Jenkins 控制台，成功和失败均输出已完成阶段。只输出阶段名及秒数，不公开状态中的配置与凭据；不新增持久化格式，不改变备份、发布或恢复顺序。

验证：`python3 scripts/test-release-tools.py` 36 项通过；`python3 -m py_compile deploy/local.py`、`git diff --check` 通过。本轮尚未生产发布，未达到五分钟验收。
