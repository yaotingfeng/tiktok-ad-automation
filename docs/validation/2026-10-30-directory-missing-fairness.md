# 2026-10-30 目录缺口修复与公平派发

## 问题与选定修复

生产同租户 status 队列把新缺失对象与已有对象的到期刷新按年龄混排。真实 PostgreSQL 最小复现中，40 条旧 status 刷新会占满首批 32 个窗口，新事实触发的缺口没有获得派发；旧任务为 identity 时则能获得服务。另一个已验证问题是完整覆盖缺口经 `ad` 修复通道重拉报表，造成不必要的外部读取。

本轮直接从现有事实修目录，按 100 个引用有界推进；完整覆盖修复使用独立持久进度与真实提交结果，不制造报表成功水位。目录请求复用现有 `directory_service_v1` 键，以 `status_missing` 标记未观测对象，仍归 status 服务。原 100 ID 分片不因类别拆分；已存在但到期的对象仍是普通 status；素材子运行仍为 identity。覆盖精确匹配与去重保持，未开始请求可原位晋升，已投递或执行中的请求不改执行身份。

status 内缺口与普通刷新交替，共享原有容量；跨轮类别记录在租户游标，避免只有一个空槽时持续偏向同类。身份服务保底、租户公平、实时总窗口 32、后台窗口 8、Worker 并发及平台限额均保持。游标只跟随实际新派发提交，分页续投不推进轮次。

## 数据与发布方案

候选保留生产 `5f25b243dd5bfd162d964c6467947ce542a1635e` 的小程序目录恢复修复。只选择同步分支的完整已审查差异，不把主分支未发布迁移带入生产。

选定迁移 `0064_closeout_job_scope → 0066_directory_status_turn`，只在小表 `directory_dispatch_cursor` 增加可空 Boolean 列 `last_status_missing`，没有默认值，也不改写广告、报表或历史任务。全部 11 角色先正常退出至零 Pod，再由精确候选镜像运行一次 Alembic；SQL 限时 5 秒、锁等待 500ms。迁移 Job 不重试。保留原配置、正常退出宽限、发布锁、模板 CAS 与精确版本验收。

迁移结果不明时不恢复旧程序、不重跑。只读证明确为旧 head 且列不存在时，才可以恢复原版本；DDL 成功后即使回退程序也保留新列，不在线 downgrade。旧消费者会剥离现有服务键，查询与 partition 不变，但旧调度不识别 status_missing，会失去新 status 公平保证；不得称回退仍保持新调度效果。

按既有用户授权，本轮不新建备份、不恢复演练、不等待历史积压全部排空。以上是选定发布方案，尚不是生产成功记录。

## 验证与验收口径

健康修复已完成真实 PostgreSQL/Redis 的限时、锁冲突、提交后续跑与大小账户公平验证。0066 已在本地 PostgreSQL 从 0064 正常升级；无 server default，迁移图仅有本次一个新增 head。其他针对性回归与生产结果在完成后补记。

生产验收应对齐实际版本、完整健康覆盖时间、当前目录缺口及新旧任务分别完成的速度。历史运行的 MATERIALS_INCOMPLETE 是当次发布审计，不能当作当前尚未补齐数量；服务 Ready 和测试通过也不能替代生产缺口改善。

### 发布前只读实测与容量边界

新候选查询在生产数据上只读 EXPLAIN ANALYZE 为 1,690.458ms，规划 189.229ms；旧 schema 尚无新列，探针仅将新游标值替换为初始 NULL，不加锁、不写入。该结果证明当前数据规模下候选查询可完成，不能代替真实领取并发验证。

当前共享库只读连接采样：项目 62、其他数据库 37、同库无法归属 0。原项目池理论上限 153，加其他 37 与运维预留 10 为 200，超过普通连接上限 197；这是已有静态超配风险，不能报告为容量充足。本轮独立审查选定等容量修复例外：旧/新均 41 个 prefork、池上限均 153、原窗口和资源不增，正常零 Pod 切换无版本重叠；实际总连接加预留必须仍低于 197，发布后继续核对连接错误。此例外只适用于本次不增加容量的软件修复，不能据此批准扩容或声称已解决共享数据库容量问题。
