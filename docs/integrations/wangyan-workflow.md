# Wangyan durable promotion-link workflow

The transport contract and public-source evidence are recorded in [wangyan-link-protocol.md](wangyan-link-protocol.md). This document describes the application workflow, not a server idempotency guarantee or a live acceptance result.

`run_link_item` retains the existing provider task's original actor, tenant-scoped item claim and remote scope. A production task has a 45-second prefork hard deadline and a 60-second claim. Every invocation performs at most one HTTP request, after committing and closing the database transaction. Tenant permissions, the original actor, current connection status, credential generation and verified application membership are checked again before each request. Search and history reads use the same permission boundary as creation.

History is scanned before creation, 20 rows per committed task. The checkpoint stores a fixed-size scan identity, cursor, original total, counts and one candidate. Each observed remote ID, including rows excluded by platform or episode, receives an indexed `wy_seen` effect keyed by scan identity and remote ID. Repeated IDs across pages, changing totals, incomplete pages, invalid scope and the 10,000-page engineering bound stop the lookup without authorizing a POST. Read observations and the updated cursor commit together. A short page is not independently treated as an absence proof.

For ordinary reuse, the workflow selects the lowest numeric ID among matching links with a supplied URL, then reads that exact ID. When matching records exist but none supplies a URL, it reads a known record and keeps the missing URL unresolved; it does not create over that history. The exact read verifies current app, opaque drama ID, episode, platform and ID, and uses the formally selected title with the public attribution renderer. Numeric `drama_int_id` is only an attribution field. URLs, attribution IDs and protected names are never synthesized from missing evidence.

A completed empty history permits one durable create effect. Before HTTP, its persisted intent contains the app-scoped drama and episode and a stable internal `promote_name` derived from the effect UUID. The effect is committed as `sending`. A duplicate worker or an expired claim encounters the existing effect and enters read recovery; it never resets the effect to permit a second POST. The application does not use a Jiashu channel placeholder as a Wangyan remote ID.

A returned ID is committed in a separate successful `wy_receipt` effect before checking post-request authority or leaving the HTTP client scope. A failed PostgreSQL receipt transaction is rolled back and retried once in a fresh transaction while the response is still available. Receipts survive an expired item nonce and do not replace a newer owner's checkpoint. Local checkpoint failure after receipt persistence leaves the item `result_unknown`, retaining an exact-ID read path.

A valid code-zero acknowledgement without an ID, a malformed acknowledgement, or a lost response remains uncertain. Recovery first consumes any known receipt. Otherwise it repeats a complete bounded history scan and requires exactly one record with the original stable name and matching configuration across the entire result. It then performs an exact-ID read and rechecks that name. Only an already persisted direct POST receipt for that exact ID allows an omitted optional name on readback; all scope, configuration and attribution fields must still match. A nonempty wrong name is always rejected for this create, and an ID found through history still requires the original name. Empty or multiple matches never become `confirmed_absent`, and never permit another POST. A lookup that fails completeness during unknown-create recovery remains unknown.

An explicit remote rejection remains failed. A proven configuration conflict keeps `config_conflict` and its original safe error code, retaining any actual ID and preventing replay. Missing evidence, local failures and temporary actor denial retain a read-only recovery entry. The existing provider task controls backoff: retry round is capped at eight, delay at 300 seconds, with continued bounded recovery rather than an unbounded inner loop. Active/unknown effect rows retain the exclusive remote scope; successful read audit and `wy_seen` rows do not masquerade as pending writes.

Credential generations remain frozen under the existing provider workflow rule. A changed generation does not silently replace the original create intent or authorize a fresh write. A restored role with the same verified connection generation may resume reads. Adoption of a newly authenticated generation requires a separate explicit recovery policy; this implementation does not bypass that gate.

The regression suite uses real isolated PostgreSQL databases and the actual HTTP adapter with synthetic transport responses. It covers cross-page duplication, total changes, wrong opaque scope, ordinary multiple-link reuse, accepted replies with and without IDs, unique/empty/ambiguous unknown recovery, duplicate workers, late receipts, real PostgreSQL transaction failures, cleanup interruption, authority revocation and exact-name/configuration revalidation. The acceptance fixture continues through real draft preparation, Scene/capability tasks, freeze, submission, official SDK serialization and target material/cover verification. The fixture does not seed ready promotion links or target assets.

Deployment still requires authorized verification of the server's complete date-range coverage, total semantics and exact-ID behavior. The explicit 1970-to-fixed-end range and stable totals are implementation contracts supported by the public client; offline tests cannot prove hidden server truncation or concurrent snapshot behavior. No live provider, TikTok or S3 write was made for these tests.
