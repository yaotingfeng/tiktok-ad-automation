## Reproduction and boundaries

Run from `backend/` with a private `DATABASE_URL` naming an explicit PostgreSQL `*_test` database and `TEST_REDIS_URL` selecting a separate nonzero Redis database. The base database is only a connection template. Each run creates, migrates and drops its own randomly named database with a checked ownership marker. The failure regression checks that an interrupted scenario drops its own database and persists only a safe failure type. External DNS is disabled; strict transport doubles handle official-SDK GETs and provider search. No advertising executor, real TikTok/provider endpoint or object-storage service is called.

```sh
TEST_REDIS_URL=redis://127.0.0.1:16379/8 uv run python scripts/benchmark_batches.py \
  --accounts 100000 --dramas 200 --target-accounts 1000 \
  --group-size 10 --creative-count 2 --seed 20260908 \
  --output ../docs/acceptance/capacity-run-grand.json
```

Use `--directory-only --accounts 1000`, then 10000 and 100000 for directory measurements. No product page-size limit is changed: every directory and preview response contains at most 100 items. The older plan's example of 200 was corrected to the actual API contract.

The harness seeds synthetic source inventory and verified provider-link history. It executes real BC capability pagination/publication and official-SDK Scene refresh, provider search and normal local-link reuse, draft preparation, immutable preview generation and submission expansion. Scene/material readiness, permission resolution and the planner are not replaced. No empty READY preview is inserted. The fixed seed controls synthetic material identities; service-generated IDs and names retain normal behavior.

Task bodies run synchronously with only the prefork runtime guard substituted. These are database/CPU measurements, not deployed Celery throughput or platform QPS. The scheduling probe uses the real fair outbox, a captured broker transport and an actual first T2 preview task while T1 has pending work. Its reported latency is that specific local probe, not an end-to-end production latency promise. Eight concurrent thread clients test the shared Redis admission boundary; they do not simulate eight deployed prefork processes.

The baseline host is macOS arm64, 10 logical CPUs and 16 GiB RAM, with about 120 GiB free disk before the grand run. PostgreSQL 17.5 runs natively through Homebrew: shared_buffers 128 MiB, work_mem 4 MiB, effective_cache_size 4 GiB, max_wal_size 1 GiB, checkpoint_timeout 300 seconds and effective_io_concurrency 0; these settings were observed without changing the running benchmark. Individual JSON artifacts contain Python/PostgreSQL versions; newer runs also record relevant PostgreSQL settings and exact source revision. Other development processes share the host, so elapsed-time comparisons are observational. SQL counts and saved query plans explain the changes independently of timing variance.

## Default large-BC preparation

The default BC evidence age changed from 14,400 to 86,400 seconds; accepted engineering values remain 60..86400. Expiry stays anchored to the first successful observation and is not extended on subsequent pages or completion. At the former 5-second outbox cadence, 100k accounts require 2,000 role-read pages and 1,000 publication pages, plus a possible terminal delivery. The old four-hour default was shorter than the 15,000-second lower bound even before work and scheduling overhead. This value is a cache policy, not an API permission lifetime or platform limit.

The first grand attempt found another concrete blocker: the capability parser imposed 1,000 total pages, effectively rejecting all directories above 50,000 accounts. The parser now accepts consistent pages/counts within its PostgreSQL Integer storage range, retaining strict integer types, 50-row pages, exact totals and duplicate checks. The 100k first-page regression exercises the actual generated SDK and real PostgreSQL. `capacity-run-grand-page-cap.json` retains the incomplete failed attempt; it is not a successful capacity result.

Pure `expand_submission(limit=100)` took 531 calls for 1,000 units. At one such call per 5-second delivery, a 200k-unit expansion would have a roughly 6.1-day transport lower bound. The integrated worker now processes several bounded short-transaction pages in one deadline-limited delivery. Its measurements below remain distinct from this model and the direct-function benchmark.

## Separate delivery and index measurements

The integration's multi-page worker was measured in a second isolated worktree based on `8bc56e2` plus `6895802` and `3655936`. The repeatable script is `backend/scripts/benchmark_delivery.py` (implementation `f70c7d0`, metadata follow-up `d1fcaf8`). It runs the real SDK-transport preparation and frozen preview, then the actual outbox and current-message-ID-fenced `process_submission`, with a configured five-second publisher cadence. Ordinary unit messages are acknowledged by the captured broker but are not executed: this measures expansion, not advertising completion. The benchmark's publisher and task bodies are sequential in one process, so it does not model a concurrently ticking deployed Beat process.

| 1,000 units / 51,000 steps | Actual publication rounds | Expansion wall time | T1 pending messages when T2 submitted | T2 102-step expansion after submission |
| --- | ---: | ---: | ---: | ---: |
| First delivery run | 9 | 73.431 s | 165 | 45.5 ms |
| Repeat with SQL timing | 8 | 79.236 s | 163 | 40.2 ms |

T2 entered the next fair publication round; in these runs the next round could start immediately because the preceding T1 task had already exceeded the publisher's five-second interval. Each T1 delivery stopped after at most 100 short committed pages or its ten-second budget plus the currently executing bounded page; the largest observed delivery was 10.204 seconds. The profiled repeat spent 57.834 seconds in 1,503 ExecutionStep INSERT statements and 10.283 seconds in 2,505 candidate queries (largest candidate query 35.3 ms). Shared-host and concurrent PostgreSQL work remain part of the measurement conditions; these data do not establish why individual insert calls varied. Sources: `capacity-run-delivery-1000.json`, `capacity-run-delivery-profiled-1000.json`.

The bounded multi-round publisher was then measured from clean source `d3a1c1b`, integrating `1e7ebf2` and the priority-index fix. Reproduce with `python scripts/benchmark_delivery.py --publisher drain --output <path>`; it selects the new one-second cadence unless overridden. The same 1,000-unit / 51,000-step scenario expanded in 34.510 seconds over six publication cycles. T2 entered behind 159 genuine T1 messages and completed its 102-step expansion in the next fair cycle, 76.1ms after submission. This elapsed-time difference from earlier runs is observational on a shared host; it is not solely attributable to publisher configuration.

Across expansion and its remaining ordinary-message tail, 12 actual `drain_dispatch` calls published 1,009 messages to the captured broker. The highest single call published 100 T1 messages (102 total when T2 also had work); publishing itself consumed 0.353 seconds in total and at most 0.041 seconds per call. After expansion completed, the remaining 505 ordinary messages drained over six calls / 5.022 seconds with the one-second cadence. This phase demonstrates local publication at the configured 100-messages/second tenant ceiling under these conditions, without executing any ordinary unit message. Peak RSS was 167,034,880 B and the owned database was dropped. Exact per-call counts and timings: `capacity-run-delivery-drain-1000.json`.

A separate SQL microbenchmark of the new expansion-priority selection seeded 100,000 older ordinary pending records and one newer expander in its own disposable database. The actual `LIMIT 1 FOR UPDATE SKIP LOCKED` query used 6.697 ms and 1,820 shared-buffer hits with existing indexes. An added partial `(tenant_id, available_at, id)` index restricted to unpublished `builds.expand_submission` records reduced this to 0.017 ms and two hits. The probe creates its index only in its disposable database. Production fix `a97f4d5` adds migration `0013_dispatch_expansion_index` and the fixed task predicates. Both actual-service SQL regressions turned red to green; 65 PostgreSQL queue/expansion tests pass, including forced generic/automatic prepared plans, tenant/time binding, fresh migration, downgrade/upgrade and Alembic schema comparison. Reproduce with `python scripts/benchmark_dispatch_index.py --rows 100000 --output <path>`; the base URL must still name an explicit `*_test` database. The exact redacted plans are in `capacity-run-expansion-slot-index.json`. With task_name kept as a prepared-statement parameter, PostgreSQL's default automatic plan selection switched after five custom plans to a generic plan (six generic / five custom executions recorded), losing the partial-index implication and scanning 2,315 buffers / 12.765 ms. A fixed task-name SQL literal retained the partial index even under forced generic planning (three buffers / 0.010 ms). The partial index must be paired with a trusted constant task predicate, while tenant/time inputs remain bound. The production fix uses `literal_execute=True` only for the fixed application task name in both priority publication and the other-tenant fairness probe.

A further deployment bound remains distinct from planning capacity: at the original five-second outbox interval and five messages per tenant per round, a single tenant has a one-message-per-second transport ceiling. If each of the grand plan's 10.2 million execution steps requires one delivery, that alone is about 118 days before extra scheduling/dependency messages and platform rate limits. Multi-page expansion fixes the expansion-specific lower bound, not this downstream delivery ceiling. The integrated bounded publisher removes this former ceiling; the measured one-second / 100-message tenant configuration implies a roughly 28.3-hour ideal transport floor for 10.2m separately delivered steps, still excluding additional messages, worker time, retries and actual platform admission. Evidence expiry and scope validation remain enforced while queued work progresses. No benchmark result here should be presented as proof of fast end-to-end production ad creation.

Daily budget sums exactly to USD 20,000,000; no unit is blocked. Preview generation required 5,024 bounded calls and 6,445.129 seconds. All 2,000 preview pages returned at most 100 strictly ordered, nonduplicated units: P95 11.741 ms, maximum JSON response 36,652 B, total paging time 17.683 seconds.
