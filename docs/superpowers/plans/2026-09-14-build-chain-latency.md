# 广告搭建链路耗时与恢复修复

用户要求定位共享、回查、封面与 CTA 的耗时，精简冗余步骤并修复卡住的链路。

## 已核实问题

- 两部剧、两个账户展开为 90 个目标素材步骤。素材准备约 22 分钟；后续 3 个系列、3 个组、6 条广告的创建约 80 秒。
- 共享逐条读取源 MID，目标搜索取得唯一结果后仍另排一次详情查询。
- 所有素材均被强制要求图片 ID，生成封面再回查；官方 Smart+ SDK 的 image_info 为 optional，仍须核对具体视频场景。
- 两个 prefork 同时消费 resources/builds/control；周期任务积压和过早补投放大排队。
- MCP 在明确 NOT_SENT 时仍可能被归为终止失败，缺少有限重试及脱敏诊断。

## 实施顺序

1. 先用真实 PostgreSQL/Redis 和传输替身复现未发送异常；有界重试、保留发送前后边界及脱敏故障类型。
2. 根据官方条件明确视频封面策略，完善请求编解码、素材依赖、最终校验及回读，保留已冻结发送正文。
3. 减少素材重复读取，复用可靠源库存；目标搜索有完整唯一内容证据时直接完成准备，缺失/歧义继续核查。
4. 调度与资源执行分离，周期消息过期处理；保留持久 outbox 恢复，不清空队列。
5. 运行相关合同、并发、恢复与链路回归，记录效果及局限，按仓库规则聚焦提交。
6. 测试环境落地须完整备份与恢复验证；原任务恢复只处理已证明未发送的失败分支，保留既有成功广告及其冻结意图。

## 本轮实际范围与后续边界

已实现并进入本地回归：有限 NOT_SENT 重试、脱敏传输诊断、可选封面请求及历史正文最后检查、唯一完整共享搜索结果复用、周期 tick 过期。

不将以下阶段视为已完成：具体 Minis 场景省略封面的真实确认、源库存缓存/会话复用/批量共享、Worker 资源隔离、原终止 CTA 的人工安全恢复入口、测试服务器发布和发布后耗时验证。当前服务器和原广告保持不变。完整诊断见 [验收记录](../../validation/2026-09-14-build-chain-latency.md)。
