# 报表关联积压根治实施

依据：`docs/validation/2026-10-19-sync-backlog-root-cause.md`。用户已要求彻底修复生产积压。

## 合同

- 财务事实读取、完整分页发布、冻结授权与共享平台配额不变。
- 关联保留当前日与历史两类需求，避免历史大范围扫描拖慢当天；每类按租户/BC/操作者/冻结路由/账户/系列范围合并日期。
- 只合并未领取且无有效租约的任务。运行中的工作保持冻结，新增需求进入一个可合并的后继，完成旧任务不能覆盖后继。
- 扩展日期后不可拼接不同广告筛选的概览页；已验证映射保留，重置查询游标。被合并的旧任务保留审计和承接任务 ID。
- 当前/历史关联各有最低在途份额，空闲可借用，均使用现有 Worker 与准入额度；关联步骤有界并在每页后提交。
- 尚缺视频或平台身份的工作明确等待依赖/复核，不能标完成。相同依赖期间不反复创建、投递空任务；有新证据则唤醒。

## 顺序与验收

1. 真实 PostgreSQL/Redis 回归复现历史饥饿、日期扩散、运行中新增丢失与负缓存空转。
2. 修复公平领取、账户需求合并、缺口判断与依赖复核；旧积压有界归并，已满足范围按事实完成。
3. 复用旧帖定位的单广告读取结果，为同一响应中的其他帖子建立确定关联；保留多广告归属不确定性。
4. 核对恢复 SQL 与健康锁竞争是否仍影响吞吐，按证据修复必要路径。
5. 运行关联、事实、规划、健康、发布门禁回归与类型检查；只提交本轮文件。
6. 涉及持久任务合同变化，发布必须完整停写备份及隔离恢复验证。按生产实际值保留开关/配额。
7. 上线后分别追踪固定旧批次的真实缺口、历史有效请求/完成、当前数据时效、依赖阻塞、重启/内存。任务合并数量不计作真实数据补齐；未验收不能称彻底解决。
