# AI 优化师统一复盘与经验闭环实施计划

日期：2026-11-13。用户已确认方案方向；本文件为待实施计划，不能作为功能已完成或真实模型验收的证明。承接 [工作台设计](../specs/2026-11-11-ai-ad-workbench-v2-design.md) 第 7 节。

## 已确认的组织方式

一个工作台复盘入口、一个主复盘 Skill，配套按需加载的专项参考方法及共用计算能力。无需用户分别启动五种复盘，不默认拆成多个 Agent 或多次模型调用。原有本机五个复盘 Skill 保留，其运行命令、BC、账户、阈值与历史授权不迁为多租户默认值。

主 Skill 固定检查目标、执行兑现、数据资格、主要瓶颈、当前策略/规则、上轮建议效果及下一轮验证。专项方法为搭建与测新、自动规则、素材、经营；放量和跨 BC 跟投方法保留为后续扩展，v1 不启用复制放量、跨 BC 执行、多方案或 A/B。现有测新 Skill 中的实验方法不能成为本期新增实验功能。

ROAS、成本、分母、完整日、成熟窗口、回测等由 TK-ADA 领域服务确定性计算；模型负责解释证据、提出假设与候选变更。输出允许证据不足、不调整和补数据需求；不能拿缺失当零，不能将观察差异写成因果结论。

## 当前真实缺口

现有 DSH 插件只有内嵌通用提示词及结构化完成工具；未加载既有复盘 Skill 或知识正文。知识引用只有元数据结构，手动及定时任务未组装方法/知识内容。报表输入依赖发起人已有查询快照，并非自动生成固定复盘数据包。经营与操作输入主要是来源元数据，历史建议及其效果没有完整进入下一轮。此前 v1 的代码与协议验收不证明这些业务能力已交付。

## 阶段 1：固定复盘数据包

影响范围：`backend/app/modules/ai_workbench/reviews.py`、独立数据包服务、现有 reporting/business/operation_logs 的只读接口与相应测试。

- [ ] 按 tenant、optimizer、BC、当前授权账户、复盘截止时刻和配置版本创建稳定发生记录；重试复用同一冻结输入。
- [ ] 调用现有本地事实和指标口径生成限定窗口的复盘数据，不依赖用户此前打开报表；不在模型任务里临时直连平台。
- [ ] 携带账户时区、当地完整日、归因成熟度、覆盖/新鲜度、币种、分母及排除原因。平台广告收入/消耗与含分成返点的经营利润分别展示，复用已有 business 计算，不自造费率。
- [ ] 组装逐剧/账户/策略版本/素材制作策略的指标、计划与真实执行、规则候选/命中/动作/未知以及相关操作事件；缺失映射明确不可用。
- [ ] 设置有界窗口、行数和任务输入预算；截断须明确且不能拿部分样本作全体结论。

验收：没有任何历史查询快照的租户也能生成数据包；两租户及同 BC 两优化师无串数据；盘中/未成熟/缺失/零值/多币种分别测试；指标与原模块同源一致；冻结后来源刷新不改旧复盘。

## 阶段 2：统一主 Skill 与专项方法

影响范围：工作台专用版本化方法资源目录、`integrations/dsh-ai-workbench/`、后端方法注册/选择服务及测试。

- [ ] 提炼 `ads-employee-review` 为主流程；从控损、测新、放量和跟投方法中抽取可复用的证据资格、执行核对、窗口、版本与反事实约束。
- [ ] 为搭建测新、自动规则、素材、经营分别提供参考方法，注明必需字段、适用条件、输出结构和不能得出的结论。
- [ ] 将旧路径、平台调用、文件/飞书写入、固定 BC/阈值及历史授权替换成当前任务数据和能力引用，不改旧本机 Skill 行为。
- [ ] 按任务实际数据与可用能力选择专项；在同一复盘任务中冻结主 Skill、专项列表、版本/内容哈希及正文，不仅保存文件路径。
- [ ] 模型仅得到任务允许的方法内容和领域能力；缺字段的专项报告不支持，不开放 shell 或原始平台工具规避限制。

验收：加载的方法正文实际出现在模型任务输入中；自动选剧/复制/跨 BC 及旧审批流程不被方法带入；固定样本能区分起量不足、回收不足和执行未落实；改变方法版本不改变旧任务。

## 阶段 3：版本化知识与隔离经验

影响范围：知识资产/版本/范围模型与 Alembic 迁移、检索或任务装配服务、管理员知识管理接口及测试。

- [ ] 分开登记公共方法、租户经验、特定 BC 案例，保存来源、适用账户/对象、有效期、证据和内容版本；历史阈值标为案例，不自动成为规则。
- [ ] 通过任务范围受控检索/装配正文；不读取其他租户私有 outputs，不把模型总结直接升级为公共知识。
- [ ] 设置相关性、时效与正文预算；冲突知识同时标注，过期或无法验证来源的内容降级为待核查。
- [ ] 冻结实际使用的内容及版本，避免只给引用 ID 却无法读取正文；凭据和内部思维链不进入知识。

验收：同名知识跨租户隔离、BC 不匹配、过期、冲突、版本变更和引用保留均有回归；原始账户/费率/历史授权不泄漏；模型能引用实际收到的知识证据。

## 阶段 4：建议效果与经验反馈闭环

影响范围：提案/决定/发布/观察关联模型、效果计算服务、下一轮证据组装、工作台复盘页面与测试。

- [ ] 贯通原问题 → 候选建议 → 采纳/拒绝/未执行 → 生效版本/对象/时间 → 观察窗口 → 实际表现。
- [ ] 明确建议未执行、执行失败、未知、观察未成熟、人工干预及配置混用；这些不能写成策略无效或策略成功。
- [ ] 下一轮带入前轮结论和验证条件，形成保留/撤回/继续观察/证据不足的决定；回退仍发布新版本，不篡改历史。
- [ ] 模型生成的经验先保存为有证据和范围的候选，满足验证条件或明确人工确认后才成为可复用经验；拒绝/过期提案不自动生效。

验收：至少两轮连续任务使用真实持久状态和确定性模型替身，验证第一轮建议、真实服务决定/发布、后续指标与第二轮复核；无随机对照时不宣称增量收益因果。

## 阶段 5：能力合同、完整验收与上线准备

- [ ] 向 DSH 提供现有策略/规则支持字段、Schema、参数范围与不支持动作的版本化能力目录；候选配置能在不写广告的情况下预校验。
- [ ] 覆盖两租户、同租户两优化师、AUTO/MANUAL、缺知识/缺数据/缺映射、上轮拒绝/未执行/生效/未知等情况。外部替身放在传输边界，锁和并发用真实 PostgreSQL/Redis。
- [ ] 验证持久化数据包→实际 Skill/知识正文→原生 DSH 会话→结构化结果→发布/待确认→下一轮反馈整条链；模型判断质量与协议通过分开报告。
- [ ] 更新迁移、输入容量、运行时配置、版本保留和部署说明。真实模型与实际租户只读复盘按明确目标配置验证；真实下单、广告写入和发布不能由设计确认推导授权。

交付标准：数据、方法、知识和反馈四层均有实际装配证据；文案报告不是验收替代物。运行链路可用、业务复盘能力完成、真实模型判断质量、真实经营效果分别记录，禁止合并宣称。
