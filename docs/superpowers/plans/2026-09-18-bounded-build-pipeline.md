# 批量搭建流水线 Implementation Plan

> 执行方式：按用户要求在当前会话持续执行，使用 executing-plans；不启动子代理、不等待重复确认。用户明确要求原批次完成前继续。

**Goal:** 完成原180组合，同时用有界并行与结果独立执行解决大批量队头阻塞。

**Architecture:** PostgreSQL持久依赖与窗口控制活跃图，准备和结果各保留一个素材槽。旧消息经正式任务重投递正确路由，原任务栅栏及外部额度保持。

**Tech Stack:** Python/SQLModel/PostgreSQL、Celery/Redis、systemd。

**Spec:** ../specs/2026-09-18-bounded-build-pipeline-design.md

## Task 6：完整封面候选查询的规划开销

- 23e版本已备份部署，RETRY累计调度416项；服务器新增六项恢复回归通过。继续观察发现封面候选完整SELECT在17时段有12次5秒SQL超时，单独窗口查询的4ms证据不能覆盖三重嵌套候选查询。
- 实际服务器只读EXPLAIN：旧查询8.85秒，JIT编译8.62秒；仅物化候选降至3.88秒仍不足。候选物化一次，绑定依赖改为排除NULL的tenant/job集合反连接，取消相关EXISTS的高估成本。新查询32.189ms且无JIT，不修改数据库配置/超时。
- 同一只读REPEATABLE READ快照比较旧/新查询，55条完整行及顺序完全相同，7.22957秒→0.02815秒；预算0.5秒通过。万组合测试同时构造1万封面/资产依赖并执行完整候选SQL，仍10个候选。
- [ ] 完整执行/封面准备与未绑定素材库回归通过后发布，核对真实超时消失并持续完成原180组合。

发布前证据：完整执行与容量15 passed /103.90秒；封面吞吐/独立素材库/封面创建和恢复98 passed /177.56秒；Ruff/格式/ty app通过。

## Task 11：同账户有界连续分页

- 实际批次40余个小批次交错逐页，期间其他共享使同账户总数变化，造成多次重启。真实只读测量建立0.978秒、首次读2.288秒、同连接第二次读0.654秒；同会话连续读取可减少重复初始化和相邻页排队间隔。
