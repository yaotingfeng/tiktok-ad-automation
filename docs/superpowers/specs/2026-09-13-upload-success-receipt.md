# 正常 URL 上传以成功回执完成入库

用户要求判断重复回查的必要性，并在非必要时移除，以减少大批量、多租户调用与等待。本决策替代既有设计中“每个成功上传仍须独立回读才可入库”的要求；未知结果恢复、租户/BC/连接隔离和原件删除确认继续生效。

## 接口与证据

- 页面提交任务到后台队列，Worker 调用 `file_video_ad_upload`，使用 `UPLOAD_BY_URL`，关闭自动修复和自动绑定。当前正常调用在同次响应给出实际 VID，不是仅返回异步任务 ID 后轮询完成的路径。
- [TikTok 官方 SDK 的上传接口说明](https://github.com/tiktok/tiktok-business-api-sdk/blob/main/python_sdk/docs/FileApi.md#ad_video_upload)明确描述上传后取得视频 ID 用于创建广告。没有据此要求每条成功上传都再调用素材查询。
- 业务成功码与严格解析的单条实际 VID 才能作为成功回执，HTTP 200、成功文案、任务 ID 或模糊嵌套 ID 均不够。
- 当前适配器只持久化 VID/MID 和请求关联证据；历史保存的原生完整样本来自查询接口。不能宣称已经核实 MCP 上传回执必定含 size/signature，也不能把本地 MD5 填成远端返回的 MD5。正常上传确认无需依赖这些字段。

## 实现与验收

1. 同步上传成功先独立保存回执，再立即完成本地入库、来源槽位/原件用途释放及清理排队，标记 `confirmation_source=upload_receipt`，不新建正常 60 秒核实任务。
2. 本地发布在客户端关闭前完成；关闭失败不能把已入库素材退回未知。若回执保存或本地发布中断，则原有持久操作及恢复任务继续处理，绝不再次上传。
3. 上传超时、丢失响应、缺有效 VID、身份冲突等才保留未知核查。恢复仍按原账户/冻结连接及文件名、摘要、大小查找并精确回读，标记 `confirmation_source=video_readback`。
4. 无新功能开关、无数据库迁移，不改变已确认导入/清理配置。旧版本已排队恢复任务对成功操作直接退出；旧未知操作继续使用既有恢复协议。
5. 回归覆盖 API/MCP 的一次 POST 直接可用、原生文本回执、重复投递无额外调用、用途和槽位释放、清理排队、回执事务失败、关闭异常、代次及权限变化、未知结果不重发。外部真实写入与模拟测试分别记录。
