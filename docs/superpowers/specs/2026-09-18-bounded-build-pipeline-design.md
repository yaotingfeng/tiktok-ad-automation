# 批量搭建流水线：有界并行与结果隔离

用户要求继续修复原 180 组合，不能以局部修复交付，且必须验证万级批量和故障恢复。仅新加坡测试服实施；不更改原提交的租户、BC、账户、预算、素材选择及 ENABLE 意图。外部额度和活跃素材执行槽总数仍为 2。

## 根因证据

- 原批次 4770 素材步骤产生大量未来准备和重复观察消息，依赖等待与过期领取没有形成有效背压。已修持久等待及旧代次退出，但历史积压仍存在。
- 结果队列实测包含 7120 视频核验、1538 封面准备和177封面核验；其中6853视频核验已过期。两个资源槽可同时被慢封面准备占用，队列轮询公平不等于结果有执行能力。
- 单组合窗口只能抑制扇出，不能作为批量吞吐的最终方案。
- 新测试确认批量规划选入未来封面，随后单任务领取拒绝，导致当前批次 cover_claim_lost。两层准入必须同源。
- 封面库存被并发共享改变时，旧实现立即阻断；已发布最多两次重新完整扫描，不以不完整库存推断不存在。

## 方案与取舍

不继续增加线程或放宽外部额度，也不让所有组合同时刷新。使用固定有界并行窗口、准备/结果独立执行槽、同一准入条件及原幂等恢复机制。保留 PostgreSQL 为持久事实、outbox 为投递来源，Redis 不承担业务真相。

1. 每提交最多10个未完成且可执行组合，按剧目再按组合排序，尽量复用同剧素材。完成/明确阻断后补入后续组合；UNKNOWN保留核查并让出窗口。每个外部请求仍受原额度、租约和权限限制。
2. MATERIAL、单封面领取、封面批量规划使用同一窗口。独立素材库操作不受搭建窗口限制；已发送批次不改写成员或重发。
3. 现有两个活跃素材槽拆成准备1、结果1；准备仅resources，结果仅resource-results。materials.prepare_cover属于准备而不是结果。广告与控制原独立槽不变。
4. 旧错误队列中的封面准备由正式Celery任务按当前注册路由重新投递同一任务身份，再由正确消费者执行。不是运维搬队列，不清消息、不改业务状态；发布失败或重复投递由既有outbox和job/revision/claim栅栏恢复。
5. 依赖未就绪保持持久等待；已知结果批读和共享去重继续原20×10/50上限，未知发送不盲目重发。未发送失败走原产品重试接口。

## 验收

- 原180组合完整创建并远端回读，已有成功对象无重复创建；测试或健康不能替代。
- 有界窗口大于1，超过窗口的图不制造同比例活跃消息；两波以上完整执行，窗口自动补位。
- 真实Redis消费者中准备槽持续占用时，结果无需等准备释放即可在3秒内开始；Linux prefork验收。
- 旧队列任务跨正确路由后保留任务ID/租户/actor/payload；重复、发布异常不跳过权限与幂等栅栏。
- 10000项负载检验队列上界与准入查询耗时，记录环境和数字；不把万条封面局部测试等同于万条广告完成。
- 故障覆盖消费者退出、重复投递、外部超时/未知、依赖失败和后续组合接续，不能出现无租约、无可恢复投递的悬挂任务。
- 完整备份/隔离恢复后统一部署；总活跃素材槽仍2，核查新增结果服务实际版本、配置、资源占用。
