# 每日操作日志留存与历史／T+1赔付核算

状态：用户于2026-11-10明确批准开始实现。实施计划见 ../plans/2026-11-10-operation-log-compensation.md；本地实现与验证记录另列，不代表已调用真实平台、完成生产补数或发布。

## 目标与现状

- 已保存的广告日报（消耗、D0收入、IAA事件）直接复用，禁止为经营看板重复建立另一套日报采集。
- `ad_object.configuration` 是最新配置，目录同步会覆盖旧值；工具内搭建冻结参数、管理执行记录可作补充依据，但不能证明所有平台UI及其它API操作均已覆盖。
- 经营赔付目前只读 `BusinessEvidence`；唯一写入口是人工登记。没有官方日志同步、每日出价还原和自动依据生成链路。这是本轮必须补齐的功能。
- `business.schedule/work`、报表近期回刷和历史回填已经存在。本轮复用现有Control/后台执行、官方SDK、冻结路由与共享频控，不新增常驻服务或另一套TikTok网关。
- 本轮聚焦操作日志及预计赔付。新剧补贴继续使用已有季度规则和日报；日志不是补贴档位的输入。不将赔付与补贴相加伪装成实际到账。

## 实施方式与范围

比较：核算时临时拉日志不能满足每日留存且重复耗费额度；另建独立采集服务会重复调度和授权机制。采用现有同步框架中的“账户操作日志”资源，先持久保存事实、覆盖及版本，再由经营模块读库核算。

适用于已明确授权并启用同步的各租户/BC，复用 `AdSyncAccount.owner_bc_id` 避免同账户在多个BC重复采集。平台事实主键归属 `tenant_id + advertiser_id`；经营计算仍限定明确BC，不合并不同租户或BC的金额。开发与替身测试不依赖某个BC的真实ID；真实联调、历史补数和发布另按用户指定范围执行。

## 官方接口和传输

官方接口：`/open_api/v1.3/changelog/task/create/`、`check/`、`download/`。create是只创建读取日志的导出任务，不创建或改变广告。按账户导出，查询跨度不超过30天；这是单次查询跨度，不推定平台历史保留期只有30天。

- 获取完整预算、出价/优化、状态及创建/删除相关日志，包含已删除对象，不只获取当前启用系列。优先一次导出完整所需日志，再按字段归类，避免逐系列重复申请。
- 统一保存导出时区，优先请求UTC+0；解析后以UTC保存事件时间，再按账户IANA时区归属业务日。账户当地一天可能不是24小时，不能用UTC日期直接切自然日。历史分片同时按UTC实际跨度检查30天上限，不能仅数30个当地日期后忽略夏令时多出的一小时。
- 使用项目锁定的官方Python SDK及统一 `gateway`／准入路径。当前已安装SDK未发现生成的changelog方法；若实施核查仍如此，通过官方 `ApiClient.call_api` 调用固定官方路径，沿用认证、期限、错误归一与共享额度，不自建HTTP客户端或业务网关。
- 三个物理接口分别注册到 `platform_quotas.SDK_ENDPOINTS`，每一次create、check、download都真实计费率/并发成本。保留原应用/租户共享上限；新操作使用已确认的读取类准入策略，不扩大部署额度或引入业务开关。
- SDK适配器提供独立 `ChangeLogReader` 合同，与报表指标解析分离。check/download具体字段及终态必须按当期官方定义和回执夹具验证，不能凭任务创建成功判定已取得日志。

接口依据：
- https://business-api.tiktok.com/portal/docs/create-a-change-log-download-task/v1.3
- https://ads.tiktok.com/gateway/docs/index?doc_id=1740579480076290
- 工作区已有真实导出结构参考：`docs/superpowers/specs/2026-10-26-tiktok-ad-wide-table-schema.md`（工作区根目录，不是本子仓库）。其成功/失败记录不当成本轮生产覆盖证明。

## 每日、近期回刷与历史补齐

1. 每个账户当地日结束后产生T+1日志需求。日报与日志是独立来源，二者均持久保存；任何一方失败都可独立恢复，不能撤销另一方已成功的事实。
2. 建议每天回刷最近7个完整日的操作日志，吸收迟到/更正；7天是本稿提出的默认。同内容重读不重复插入或无故推进经营修订。
3. 历史默认沿用经营范围的历史起点；用户请求更早区间时，生成该区间缺失需求。先服务最新完整日，再按不超过30天切片补较早历史；真实可得范围由平台回执证明。
4. 所有需求按账户和日期合并，T+1与历史重叠只保留一个事实来源。当前同步授权/归属变化后重验；冻结连接代数失效不能继续用旧导出任务发布。
5. 不在Worker里阻塞轮询。阶段为创建导出、等待、检查、下载/解析、原子发布，平台task_id及每阶段游标写数据库；等待时释放HTTP/账户并发槽并按due时间恢复。
6. 优先扩展 `ReportSyncJob` 的日志种类及progress，接入已有 `sync_control` 需求/租约/投递/恢复。日志使用独立解析/覆盖表，不伪造ad_day、素材指标或报表完成水位。实施计划需逐项列出kind、endpoint、worker路由、状态机及旧任务升级边界。
7. 最近完整日和历史分别有持久游标，历史不得挤占日报实时槽，也不能因最新窗口持续更新而永久饿死旧历史。复用现有公平调度及后台池，不新增Worker或直接调高并发。

权限/平台错误、限流和暂时网络故障分别记原因。有限退避和重试后明确等待或失败；过期task可在原需求下重新生成导出，不循环创建无限任务。create回执丢失可能产生重复读取导出，重试须有上限并保留尝试记录；事实发布仍幂等。

## 保存合同

至少包含以下逻辑数据，物理表名由实施计划确定：

| 数据 | 必须保存的内容 |
| --- | --- |
| 导出运行 | 租户、来源BC/连接及绑定代数、账户、查询起止UTC、账户时区、平台task_id、阶段、attempt、due/lease、抓取时间、错误类别、内容摘要 |
| 原始证据 | 完整导出内容或可验证的私有归档引用、摘要、格式/解析版本和来源。原文含CSV嵌套JSON时保持可回读，不只保存汇总数字 |
| 规范化操作事件 | UTC时间及原文时间/时区、对象层级及ID、父系列/广告组关系、字段、改前改后值、操作类别、来源、人工/自动/未知归因、证据引用、稳定事件身份 |
| 日期覆盖 | 账户当地日期、查询/下载/解析完整性、内容修订、已覆盖时间边界、成功空结果或失败/截断原因 |
| 配置观察 | 账户/对象、实际观察UTC、必要出价/预算/结构/优化目标/状态、来源版本、事实摘要，构成可回溯的配置锚点 |
| 系列日赔付依据 | 业务键、适用规则版本、每日最低ROAS、改价次数及归因、已知排除操作、结构证据、日志覆盖/锚点/日报修订、数值候选、资格边界及原因 |

原始和规范化事实保留可追溯版本；重抓相同数据不重复计数，出现更正保留旧版本与替代关系，不在本轮增加自动删除历史操作事实的策略。原始导出进入现有私有审计归档机制并有界分块，数据库保存摘要/引用；日志和API响应不进入Git、公开文档或普通应用日志。只向有权限的管理员展示必要业务字段，原文中的操作人等信息按现有权限保护。

没有原生日志ID时，使用稳定规范内容身份及相同内容的出现次数保留多重事件；不能只用时间+对象去重，同分钟可有多次操作。跨重试/重叠窗口幂等，不能将两次真实同额修改合并成一次。

CSV须处理引号、换行、BOM、嵌套JSON、表头和汇总行。完整官方空结果可标“成功无操作”；下载失败、未知格式、超限、截断不能标“无操作”。大导出按有界时间/对象窗口继续，不将数十MB原文反复搬入控制任务。存储原文失败时不发布完整覆盖。

## 每日出价与操作还原

日志记录的是变化，不能把“当天无改价日志”直接解释成有确定出价。还原必须具备可信配置锚点，以及从锚点到目标日所需区间的完整日志链。

- 锚点优先使用实际对象的官方创建/配置观察；工具内已确定成功的冻结创建请求及回读可提供补充，不用当前策略模板反推历史。
- 初次接入可利用当前实际配置与完整后向变更链还原；缺失创建日志不等于永远无法回算，但不能跨越未知时间段推断。
- 日内出价按每个实际生效区间求当日最低ROAS，改价次数独立统计；恢复启用不抹去同日已发生的负向操作。
- API来源不自动等于自动操作：工具中人触发的改价与规则自动改价须依据任务来源区分，外部API来源不明则记录未知。
- 官方CSV可能只精确到分钟。同一分钟多次变更应按前后值形成可验证链；顺序无法唯一还原时标歧义，不能任取排序。
- 数值单位按明确字段解析，ROAS倍数/百分数不可混用；未知标签或值不猜测、不当0。
- 系列与广告组关系使用冻结对象身份；改名不改变业务键，日志不能靠剧名或名称字符串关联。

## 赔付规则和展示边界

本轮继续支持现有已确认的CBO Smart+ Mini Dramas / D0 IAA tROAS系列日模型，不将其它产品、IAP或非CBO套同一公式。采集可保留相关对象的日志，但不扩大核算结构支持范围。

2026-11-09复核官方说明（页面更新2026年7月）：
https://ads.tiktok.com/resources/help/article/about-smart-plus-bid-protection-app-promotion-minis?lang=en-GB

已确认模型：IAA事件≥300、B×C>1.2×V0，预计 `max(0,C−V0/B)`；B为日内最低有效ROAS。使用账户当地业务日和D0收入，不用总收入代替。

按以下顺序处理：

1. 明确无消耗、事件不足、已证实的排除操作或已知规则不触发时给0及原因。不能因不需要的另一项依据缺失而遮住已确定的0。
2. 数值输入及每日出价可靠时，计算条件预计金额。日志可核验的系列暂停/删除、降预算、广告组最低预算调整、超过两次明确人工改价等按规则排除；初始化暂停创建要与投放后暂停分开。
3. 操作日志不能证明的余额不足、全部素材拒审、风险及平台最终资格保留待核；不能因此强迫所有数值候选为空，也不能把操作日志无异常宣称为平台资格已确认。
4. 出价或必要数值确实不可还原时，相关预计保持未知并说明缺失日期/字段。不可直接拿当前出价或固定1.06冒充历史；若未来提供假设出价情景，必须与真实逐日预计分开，本轮不增加该情景。

保存并返回“条件预计数值”和“依据/资格状态”，不再用单个eligible布尔把数值与完整资格混为一体。正常日核算不要求用户人工登记 `BusinessEvidence`。

既有人工记录保留审计；与自动结果冲突时显示冲突依据，不静默覆盖官方事实。仅管理员明确绑定当前依据修订作出的人工更正才可覆盖本次结果，旧人工记录不自动成为永久覆盖。原冻结历史结果/导出不改写。

页面复用经营看板的预计赔付列、金额提示和覆盖说明，不新增一排到账/资格状态列。明确区分0、未知和有数值但资格待核；未完整时展示已计算小计并标覆盖缺口，不能把小计标成完整总额。历史与T+1使用同一规则及版本。

## 核算触发与一致性

- 日报、日志、配置锚点、人工更正或规则修订改变时，只推进相关账户/业务日及可见BC的赔付来源修订；相同回执重放不触发无意义全历史重算。
- 日依据使用不可变修订/发布引用。经营任务冻结所用来源版本，逐页计算不能混用新旧日志；复用现有scope围栏和完整发布清单，新版本完成前继续显示旧完整结果并标更新中。
- 原始操作事件、解析结果、覆盖状态及日依据发布保持原子性，部分下载/解析不能推进完整水位。旧导出按原计算版本保留，权限仍在下载时复核。
- 用户查看/请求历史区间时，已保存且覆盖有效的直接核算；缺日志需求后台补齐，失败或平台不可提供的范围明确说明，不循环等待且不要求用户手工逐条录入。
- 需要调整 `business_amounts`、赔付函数及查询聚合时，保留基础经营、新剧补贴独立口径，不重置已有消耗、收入或补贴事实。

## 分阶段交付与验收

1. **日志留存链路**：SDK适配、三阶段异步导出、现有调度/恢复/授权/频控接入、原文与事件/覆盖持久化、T+1与历史公平需求。此阶段能独立证明日志保存，不宣称赔付已自动可用。
2. **日依据与自动核算**：配置锚点、历史重放、按日最低出价/操作归因、版本化条件预计及经营发布。只取得task_id或只做公式单测不能算此阶段完成。
3. **可见覆盖与验收**：预计列及小计/待核说明、历史查询补齐、真实授权范围的端到端验收。需同时证明一个历史窗口和一个T+1窗口，且能回读原日志→每日依据→公式→聚合的对应链。

必要测试：真实PG/Redis下任务租约、重启恢复、失效授权/绑定代数、并发/重复发布、多租户及账户跨BC去重；迟到/修订、空日志与失败、30天分片/边界、DST、嵌套CSV/多行JSON、重复同分钟事件、缺锚点/断链、最低出价、人工改价计数、暂停恢复、降预算、初始暂停创建、未知外部来源；严格300及1.2边界、可确定0与缺失输入、条件金额与资格待核、来源修订围栏、历史导出不变、历史及T+1全链路。所有外部替身停留在官方SDK传输边界。

本地验证与真实生产验收分开记录，不用演示数据或固定假出价宣称真实核算完成。数据库/任务合同变更通过新Alembic迁移；本轮未授权生产迁移、推送、发布、自动开启新操作或真实广告写入。未来发布时明确原 `ADS_SYNC_ENABLED` 对日志需求的影响及API/Beat/Worker同版本边界，既有值不被模板覆盖。
