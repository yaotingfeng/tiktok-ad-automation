# 构建依赖落定与 Worker 容量设计

日期：2026-09-19

## 背景与目标

测试环境两个恢复批次已经证明现有投递合并和丢消息修复能够完成任务，但运行证据仍显示两类本地无效工作：

- MATERIAL 步骤共 794 次投递、529 个唯一步骤，其中 265 次是同一步骤的后续投递。视频和封面之间的必要阶段切换不能全部删除，但已取得明确终态的回执仍会再次进入 Builds Worker 做一次本地确认。
- 40 个单元产生 132 次单元投递。代际投递是正常推进机制，现有 `wake_unit` 也会复用同一有效消息；然而每次前置完成都会把所有已到期依赖的 `due_at` 再写一次，形成无效数据库写入和锁竞争。

本次目标是在不扩大远端写入授权、不降低未知结果保护的前提下，减少确定终态的重复检查和同批唤醒写放大，并为不同配置服务器建立首次部署的 Worker 容量评估办法。

## 方案

### 1. 明确终态由恢复器直接落定 MATERIAL 步骤

`recover_material_results` 同时处理以下两类步骤：

- `UNKNOWN`：保留当前只读核查语义；只有明确 `ready` / `blocked` 才能落定，核查预算耗尽只记录原因。
- `PENDING + material_pending`：当关联分发已经进入 `ready` / `blocked` 时，复用现有租户权限、冻结路由、目标账户、当前映射和外部效果检查，直接把原步骤落为 `SUCCEEDED` / `FAILED`。

`recover_cover_results` 同样扩展到 `PENDING + cover_pending`：

- `READY` 必须取得与原素材、目标账户、冻结连接和目标视频一致的当前图片映射，才能直接成功。
- `BLOCKED` 只有在从未 armed 且没有已知图片 ID 时才是确定未发送，可直接失败。
- armed、存在候选 ID、映射不一致或权限/冻结信息不一致时保持原状态，只记录核查错误，不猜测结果。

步骤落定后仍调用 `wake_unit` 和 `finalize_submission`，因此后续 Campaign / Ad Group / Ad 的顺序和提交完成逻辑不变。

### 2. 通用依赖唤醒器不再接管已明确终态

一分钟修复循环的执行顺序保持：素材结果恢复、封面结果恢复、通用依赖唤醒。

直接恢复器已拥有 `ready` / `blocked` 的完整校验，所以 `wake_material_dependencies` 对 `material_pending` 只处理 `result_unknown`，对 `cover_pending` 只处理 `UNKNOWN`。确定终态不再生成一条 `builds.execute_step` 消息后再做同一套本地判断。

这不是删除修复安全网：如果恢复器因锁竞争本轮未领取，步骤保持等待，下一个修复周期继续处理；不会由通用唤醒器越过验证。

### 3. 单元唤醒只加速尚未到期的依赖

`wake_unit` 在单元锁内取得一次统一的当前时间，只把 `dependency_pending` / `dependency_unknown` 且 `due_at > now` 的 PENDING 步骤提前到当前时间。

已经到期的行不再重复 UPDATE。现有有效 `builds.execute_unit` 投递仍按任务名、任务键、载荷和代际复用；没有有效投递时才创建下一代。消息丢失继续由现有 repair 按原投递恢复。

## 不采用的方案

- 不把四套状态机改造成新的事件总线。本轮收益可以通过小范围状态所有权调整获得，整体重构会增加未知结果和重复远端写风险。
- 不靠提高 Builds Worker 并发掩盖无效工作。低配置测试服务器会先遭遇内存、数据库连接和上游额度瓶颈；未来生产环境也必须以实测容量而不是复制测试值来配置。
- 不做运行时自动调节并发。自动调节会让事故复现和额度控制变得困难，首次部署采用明确测量、固定配置和可回退的逐级调优。

## 首次部署容量评估

首次部署必须记录 CPU 核数、可用内存、swap、数据库和 Redis 是否同机、API 进程数、各 Worker 的单进程峰值内存，以及 `TIKTOK_CALL_POLICIES` 中各共享额度域的并发和速率限制。

固定拓扑：Beat 只允许 1 个；Control Worker 初始为 1 个。其余 Resource、Result、Build 并发按以下边界取最小值：

1. 内存边界：扣除操作系统、数据库、Redis、API 和至少 25% 安全余量后，剩余内存除以对应 Worker 实测峰值。
2. CPU 边界：CPU 密集步骤不超过可用核心；网络等待型任务只能在内存和数据库连接允许时高于核心数。
3. 数据库边界：所有 API 与 Worker 的最大连接总和必须低于连接池预算并保留运维余量。
4. 上游边界：同一额度域的有效并发不得超过 `TIKTOK_CALL_POLICIES`；超过额度的进程只会制造排队和重试。

用代表性批次逐类增加一个并发槽，每次观察队列斜率、吞吐、P50/P95、失败/限流、数据库锁等待、MemoryPeak 和 swap。只有吞吐继续提升且错误、锁等待与内存均在阈值内才保留新值。稳态不得持续使用 swap；出现 OOM、数据库连接逼近上限、平台限流上升或 P95 明显恶化即回退一级。

测试环境当前 `Resource=2、Result=1、Build=1、Control=1、Beat=1` 只是低配置服务器的保守值。未来生产首次部署必须重新评估，不能直接复制。

## 验收标准

- PENDING 的明确视频/封面成功或确定未发送失败可由恢复器直接落定，且不生成对应 Step 投递。
- UNKNOWN、armed、映射不一致、权限撤销和冻结路由变化仍不会被误判为成功或允许重传。
- 通用依赖唤醒仍能恢复真正 UNKNOWN 的依赖，但不重复投递明确终态。
- 第一次单元唤醒会提前未来到期依赖；后续唤醒不改写已经到期的行，并继续复用当前单元消息。
- 部署手册包含容量采集、计算、压测、回退和环境记录模板，并明确测试配置不能复制到生产。
- 相关真实 PostgreSQL / Redis 回归、格式和静态检查通过。
