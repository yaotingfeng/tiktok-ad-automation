# R2 临时中转与大批量视频入库设计

日期：2026-09-10。状态：已确定业务取舍的设计稿，作为独立实施计划与验收依据。

本稿补充并修订[素材中心功能设计](2026-09-08-tiktok-03-materials-design.md)中的原件保留、上传路径和批量处理规则。租户、BC、账户授权、冻结预览及广告执行规则继续遵循既有设计。本稿不表示跨账户协议或生产吞吐已经通过上线验证。

## 1. 目标与确定边界

R2 只作为临时中转，不是永久原始素材库。用户批量选择本地视频，系统将完整文件接收到私有 R2、验证内容，再向系统自动选择的一个合法源广告账户执行 TikTok URL 入库。该账户的视频 info 强校验通过，并持久化真实源账户、连接、VID、MID、可信哈希及证据后，立即排队清理对应 R2 原件。

清理不等待未来广告搭建，不要求用户预先粘贴未来所有目标账户，也不要求用户维护素材账户池。后续向目标账户分发，必须能够独立使用源账户原生共享或新获取的 TikTok 源视频预览 URL 接力；这条无 R2 原件的路径必须先开发并验证，再启用成功原件清理。

工程验收目标为单次导入 10,000 文件、20,000 文件突发。目标是有界资源、可靠恢复、正确隔离和可测吞吐，不预先承诺每天完成数量、固定上传速度或账户数量。

## 2. 用户流程

1. 用户选择当前租户与 BC，批量添加本地视频。继续提示文件名包含完整剧目名称；上传不绑定剧目。
2. 创建父导入会话，保存文件清单元数据，按不超过 200 项的子批次逐步登记。配额不足的文件显示“等待暂存空间”，不继续签发上传权限。
3. 浏览器在有限文件及分片窗口内直传 R2。完整接收、内容校验、等待 TikTok、处理中、已入库、结果待核实、原件清理等进度分别展示。
4. 后台从当前可用授权中选择一个源广告账户，完成 URL 入库和 info 核实。用户无需等待广告搭建才能释放 R2 空间。
5. 视频已入库后即可保留在素材目录中。R2 删除失败只影响清理状态，不把已经核实的 TikTok 视频重新标为上传失败，也不重新上传成功视频。
6. 后续搭建按冻结素材身份和目标账户执行分发；目标视频和目标封面分别核实。源 VID、目标 VID、MID、图片 ID 不混用。

关闭页面不取消已接收文件的后台工作。浏览器刷新后，未传完的文件需要重新选择并核对；页面不得声称已永久获得本地文件访问能力。

## 3. 数据与状态分离

保留素材主记录及历史，不因 R2 清理而删除素材、上传尝试、分发、封面或搭建快照。建议以以下逻辑实体组织持久状态；具体表名与迁移顺序由实施计划确定。

| 对象 | 必须保留的事实 |
| --- | --- |
| 素材记录 | tenant、BC、内部 material ID、原始文件名、大小、媒体类型、时长/尺寸、可信 SHA-256/MD5、摘要验证时间与来源 |
| 原件代次 | material ID、递增 object_generation、不可变对象键、预计/实际字节、multipart 身份、校验及清理状态 |
| 父导入会话与子批次 | 原始请求幂等键、操作者、固定文件清单身份、分段登记游标、各阶段计数、当前调度身份 |
| 暂存预留与使用租约 | tenant、对象代次、预留字节、使用目的、关联操作、nonce、期限、是否已签发拉取权限 |
| 上传/分发操作 | 实际源与目标账户及连接、路径、稳定远端文件名、请求摘要、发送事实、已知远端 ID、核实分页进度、认领与投递版本 |
| 账户素材与封面 | 实际账户 VID/MID、可用性、checked_at；目标 image_id、绑定 video_id、封面独立状态及回执 |
| 清理任务 | 对象代次、清理原因、资格证据、认领版本、delete/abort 结果、HEAD 确认时间、错误与重试时间 |

原件生命周期为 `waiting_capacity → reserved → receiving → stored → validating → verified → cleanup_pending → deleting → deleted`，删除结果未知为 `delete_unknown`，非预期丢失为 `missing`。stored 只表示接收完整，verified 才表示可信摘要落库；失败、保留到期和需处理原因独立记录，不能等价于对象消失。对象是否存在、视频是否可用、封面是否可用是三个不同维度，不用单一 `available` 表示全部。

现有 `storage_state` 的 receiving/stored/unavailable 无法完整表达主动清理和删除未知，需要迁移或补充对应状态。主动清理后，`original_available=false`，平台状态仍可为 available，已接收字节和入库完成事实保留。原件清理中、清理失败和异常丢失应可区分。

### 3.1 对象键与去重

对象键使用 tenant、BC、material ID 和 object_generation 构成不可变命名，例如 `tenants/{tenant_id}/bc/{bc_id}/materials/{material_id}/{generation}/original`。服务端从已授权记录生成规范键，拒绝客户端指定任意键。任何重传都使用新代次，旧清理任务只能删除其绑定代次。

临时文件与内容去重仅在同一 tenant + BC 内进行，不使用全局 SHA-256 对象共享，不由哈希推断跨租户读取权限。同内容不同文件名仍保留各自导入身份和检索入口。若复用仍存在的原件代次，必须有显式引用及使用计数；若复用已核实的源账户素材，仍需验证当前授权和映射事实。客户端声明的哈希仅为候选提示。

## 4. R2 接收与可信内容校验

浏览器通过短时预签名权限向私有 R2 S3 API 直传。业务 API 不转发文件字节。签发分片权限前，必须已取得对应对象代次的全文件预计字节预留，并确认当前租户上传权限、multipart 身份及窗口资格。

完整 multipart 接收后验证 HEAD 的字节数、媒体类型和 tenant/material/generation 元数据。保留一个有界校验 Worker 从 R2 流式读取，计算可信 SHA-256 和整文件 MD5；multipart ETag 不是整文件 MD5。需要媒体探测时可写入私有临时文件供 ffprobe 使用，限制字节、执行时间、磁盘及并发，正常、失败、取消均在 finally 清理临时资源。

因此本方案仍有校验 Worker 读取视频字节；它消除了 API 字节转发与 TikTok SDK `video_file` 的全量文件读取，不声称所有服务都不读取或中转字节。校验只对一个不可变对象代次产生可信证据；对象代次、长度或摘要不一致必须阻断入库。

校验必须在数据库短事务认领后执行，网络读取及 ffprobe 不持数据库锁。校验结果提交时检查 nonce 和对象代次，过期 worker 不得覆盖新 owner。

## 5. 源广告账户选择与 URL 入库

系统在当前 tenant + BC 中，按最新账户归属、有效连接和实际上传权限自动选择源账户。采用租户公平调度及账户在途数、负载、冷却信息选取，不能沿用当前按账户 ID 排序取首个的固定策略。选择后持久化真实账户与连接；后续默认选择变化不改写历史。

初始 TikTok 入库并发为每个源广告账户 1，可配置到经实测证明安全的额度，同时遵守 App、endpoint、tenant 和账户共享准入。源账户数量由当前合法授权决定，不固定为某个 BC、四个账户或历史测速账号，不让用户另行配置“素材账户”。

### 5.1 发送契约

- 使用固定版本官方 `FileApi.ad_video_upload` 的 URL 入口：`upload_type=UPLOAD_BY_URL`、`video_url`、目标 advertiser_id、稳定且唯一的 file_name；具体签名、可选字段与响应语义须通过官方 SDK 契约测试确认，不手写替代 HTTP。
- 在实际发送前取得原件使用租约、当前授权与 Redis 准入，签发新的私有 GET URL。建议拉取 URL TTL 初始 2 小时，可配置；这是工程起始值，发布前需验证 TikTok 实际拉取与处理时序。队列中只存对象代次，不提前批量签 URL。
- 再次检查原件仍可供拉取、认领有效、账户/连接未改变，持久化 ARMED/发送事实及不含签名 URL 的稳定请求摘要，提交并关闭事务后调用 SDK。
- 签名 URL、签名查询串、凭据不进入数据库、队列、浏览器恢复存储或日志。SDK/http 日志和异常脱敏覆盖 video_url、image_url 及重定向信息。
- 上传响应只证明接收；优先持久化任何已知 VID/MID，再处理清理、权限变化或后续失败。info 必须对目标账户、实际 VID、displayable、可信内容签名及必要媒体字段作强校验。缺少必需标识或字段时保持待核实，不宣称完成。
- 强校验成功后，在同一可靠提交中保存源映射与完成事实，并通过 outbox 安排 R2 清理。视频入库成功与清理重试独立。

上传与核实继续采用真实 prefork 硬期限、SDK 超时、长于执行硬期限及清理余量的 Redis 租约和持久认领。HTTP 发送结束不代表异步拉取结束；原件使用状态不能仅随 Python SDK 作用域退出而释放。

### 5.2 未知结果与重试

超时、连接中断、进程退出、5xx 或本地提交失败必须区分“明确未发送”和“可能已发送”。可能已发送的操作保留原账户、原连接、稳定远端名称、已知 ID 与证据，只进行有界只读回查。空页、暂时查不到、签名过期或 worker lease 到期，都不是远端未生效证明。

已知 ID 优先 exact info；未知 ID 按原归属证据分页查找，分页范围、总量和唯一候选均需核实。不得在未知状态换账户、换原件代次、换共享/接力路径或再次 POST。只有明确未发送或已证实无远端效果的失败才能建立新的安全尝试。

## 6. 原件清理后的目标分发与封面

**启用立即清理的发布前置条件：至少一条独立于 R2 的源→目标路径已经通过官方 SDK 合约验证与受控发布验证，且系统对其适用权限范围有真实证据。** 尚未完成时不能将本设计标为已交付，也不能打开成功对象自动清理开关。

分发按以下顺序选择：

1. 当前目标已有新鲜、合法、已核实的映射，直接复用；映射过期时按已知目标 VID 回读。
2. 源与目标满足已核实的原生共享条件，使用官方 Creative Asset Share；保存真实 source MID、实际授权和目标映射，不能将 MID 当作 VID。
3. 原生共享不适用且操作尚未发送时，从当前仍合法可读的源账户通过官方 SDK 新取视频 preview URL，向目标执行官方 URL 入库。源预览 URL 只在内存短时使用，不保存为永久视频源，不使用历史过期链接或未经授权的任意 URL。
4. 无合法源、源链接缺失、权限不明或协议尚未支持时明确 blocked，提示恢复授权、重新上传原文件等真实可执行路径。R2 已清理不是可以偷偷恢复原件上传的理由。

各路径共用素材→目标的唯一未完成操作和发送围栏。已发送的共享或接力结果未知时只能核实原路径，不能自动切换。源账户与目标账户相同也必须依据当前账户映射核实。目标返回的 VID 可能不同于源 VID，后续广告与核查使用目标实际 VID。

目标封面继续独立运行：目标 video info/官方候选封面接口获取 URL，上传目标 image asset，再按已知 image_id 核实。封面 job 绑定目标 video_id；视频变化使旧封面失效。不能复制源账户 image_id，也不能假设 video info 直接返回可投放 image_id。封面处理和已核实的目标资产回查不依赖 R2 原件，必须在原件已删除的验收环境中证明。

本地素材匹配保留目录和合法源资产。预览 readiness 仍只读，不发 SDK、不排上传或共享工作；根据本地已核实能力和资产事实返回 ready/preparable/blocked。冻结与执行之间原件被清理时，执行沿已冻结的素材身份走已验证的无原件路径，不读取新策略、不恢复被清理的旧对象，也不修改冻结意图。

## 7. 视频预览、UI 与恢复语义

原件 GET 预览只在对应代次仍可读取时提供；清理后明确显示“原件已清理，视频保留在 TikTok 源账户”。如提供视频播放，需通过独立、当前授权的源视频信息刷新流程获得有效预览地址，短时返回且 no-store，不把旧 R2 签名或历史 TikTok URL 留作永久链接。无可用预览地址时显示准确原因，不伪造播放地址。既有只读目录/冻结预览接口不隐式执行外部调用。

上传列表、批次和详情需分开显示：文件接收完成、内容校验、TikTok 入库状态、实际源账户、原件清理状态。`received_bytes` 表示已经接收的事实，不因删除回到零。`can_retry` 根据实际未发送证据、对象代次和远端结果产生，不能仅依据 `storage_state==stored` 决定。

删除后的素材仍可有 available 状态，封面仍可有 pending/unknown 状态。不存在合法分发路径时，预览必须解释具体限制，不把“历史源账户有 MID”标为可以提交。

## 8. 暂存窗口与清理互斥

### 8.1 配额与背压

默认暂存窗口建议为全局 8 GiB、每租户 2 GiB，均为保守、可调整的工程配置，不是 R2 容量限制。预留覆盖正在 multipart 上传、完整原件、正在验证/拉取、删除待确认和删除结果未知的字节。完成 multipart 不重复扣费；同一幂等对象代次不重复预留。

在获得全文件预计字节预留前，不签发任何该文件的 part URL。窗口满时保留排队元数据并按租户公平让出，不继续灌入 R2。单个文件超过当前可用配置上限时明确说明工程容量限制，等待管理员调整或拒绝该项，不能永久占队首而阻塞其他文件。

只有 exact 对象 DELETE 后 HEAD 确认不存在，或未完成 multipart 已确认 abort 且对应对象不存在，才能幂等释放预留。删除请求发出、返回超时、TTL 到期及数据库标记过期均不释放字节。周期对账核实实际对象/分片与预留，修复崩溃留下的欠账；不能靠重启清空配额。

### 8.2 使用与删除的竞争

所有校验读取、原件预览能力签发和 TikTok 拉取必须先登记原件使用状态。清理资格判定和使用租约领取共用对象代次锁序/版本，在短事务中互斥；进入 deleting 后拒绝新租约和新签名。

已有校验 worker 的本地读取和正在拉取的远端操作必须结束或被安全确认后才能删。签名记录可保存签发目的、时间和失效时间，不保存完整 URL。浏览器原件预览使用期最长 5 分钟；签名尚有效时，清理任务立即入队但最多等待该使用期结束。源入库完成并具备清理资格后，不再为原件预览续签或增加新的预览使用期，避免反复播放无限推迟删除；UI 优先转用合法 TikTok 源视频预览，该路径不持有 R2 使用租约。远端拉取不能仅因签名过期或 worker 认领过期便视为结束。

清理任务绑定不可变 key + object_generation，领取后关事务再调用 S3，结果以 nonce 围栏落库。DELETE 成功回包也需 HEAD 确认；DELETE/HEAD 超时进入清理待核实，重试只作用于相同旧代次，不影响后来重传。视频成功回执必须先落库，再尝试安排或执行清理；清理异常不能吞掉视频成功事实。

“立即清理”指满足入库及使用条件后立即进入主动删除队列，不等待日级生命周期扫描；外部删除服务异常时通过重试与告警完成，不能承诺瞬时物理消失。

### 8.3 失败、放弃与孤儿的有限处理

建议可配置起始值：

| 场景 | 保留与处理策略 |
| --- | --- |
| 源入库强校验成功 | 立即排队主动 DELETE；有正在使用的租约时等待其安全结束 |
| 明确未发送/明确无效果的失败 | 最后一次实质进展后最多 24 小时供恢复，届时安全关闭该尝试并主动清理；恢复须重新上传已删除原件 |
| 用户放弃且尚未发送 | 关闭后续写调度，释放文件引用并主动 abort/delete；已有签名及使用需先安全收尾 |
| 未完成 multipart 或无关联原件 | 24 小时无实质进展后进入对账候选；重验所有权、代次、任务/租约及已发送证据后 abort/delete，不能只按创建时间扫桶删除 |
| 已发送但结果未知，包括用户此时放弃 | 不按年龄自动删或推断远端未读；继续原操作有界回查。24 小时未解决则标记异常并告警，冻结该对象后续摄入/写重试，进入人工核查；占用仍计入窗口，不能无上限继续接收新字节 |
| 删除结果未知或存储不可用 | 保留配额，指数退避复查；建议 1 小时持续失败告警，24 小时升级处理，不伪造已删除 |

普通失败、放弃和孤儿必须具备自动有限清理路径；未知已发送是明确异常队列，不作为正常长期保留方式。人工核查只用于这些异常，不增加正常上传或广告搭建的二次确认。人工放弃也不能绕过未知远端拉取的安全判断。配额和冻结摄入使未解决异常无法无限积压字节。

## 9. 10,000–20,000 文件导入

父导入会话记录整个导入意图与永久请求幂等身份，子批次不超过 200 文件，后台有界展开。避免一次 HTTP 请求创建数万对象、一次事务展开全部文件或一次响应返回全部进度。子批登记重投、响应丢失均复用原身份；原请求键不得绑定不同清单。

服务器提供父会话摘要及每页最多 100 的文件/子批进度分页，游标绑定 tenant、BC、父会话和筛选范围。数量、字节与阶段变化采用带版本/事件幂等保护的增量统计，并有只读或受控对账；每次单文件变化不能锁住父会话后扫描整个导入。三类计数应区分计划、接收和入库/清理完成，保证总量守恒。

浏览器使用有界窗口调度文件与分片，建议起始 4 个文件、每文件 2 个分片，可调但同时受服务端预留限制。列表分页或虚拟化，避免完整渲染两万行和每次更新全清单扫描。分片哈希按有限块计算，错误退避而非紧密重试；权限撤回和租户/BC 切换停止未完成的本地任务。

IndexedDB 保存父/子会话身份、文件指纹、分片号/ETag/块摘要和待确认状态，分项更新并清理已完成传输元数据。不得存储签名 URL、文件 Blob、账户凭据或永久文件句柄。刷新后重新选择未完成文件，按原记录的文件名、长度、修改时间及已上传块摘要匹配；仅同名同大小不足以续传。匹配歧义不静默挑选。

浏览器关闭后，已完整进入 R2 的任务由后台继续；尚未上传完整的任务可等待重选至有限清理期。存储配额不足或 IndexedDB 不可用时给出准确恢复限制，不假装已具备持久续传能力。

## 10. R2 部署要求

- 使用私有桶与 R2 S3 API endpoint，region 为 `auto`。新部署单独配置所需最小权限凭据，不索取、复制或引用历史测速 secret、真实账户 ID 或旧运行环境默认值。
- 使用 S3-compatible 数据面；`CreateMultipartUpload` 不发送 ACL 参数。私有访问由凭据、桶配置和短时签名控制。
- CORS 限定正式前端 origin，允许所需 PUT/GET/HEAD，暴露 ETag，并允许客户端实际使用的必要请求头。不能用宽泛 CORS 代替身份与对象权限校验。
- 缺少 R2 endpoint、bucket、访问凭据、正式 origin 或所需服务配置时，上传入口返回明确不可执行原因，禁止签发无效 URL 或接收无法恢复的字节。已存在的合法 TikTok 映射读取不应因 R2 不可用而整体失效。
- R2 桶容量为 Unlimited；价格中的 10 GB-month 免费额度不是桶总容量。本系统 8/2 GiB 窗口是独立的应用背压措施。
- R2 multipart 最大 10,000 parts，part 划分还须满足当前官方限制；应用单文件工程上限独立验证并展示。
- 生命周期通常不能满足即时删除：一般到期处理在 24 小时内发生，未完成 multipart 默认在 7 天后清理。成功对象依赖应用主动 DELETE + HEAD，不依赖桶生命周期。仅对未完成 multipart 设置生命周期兜底，不能设置会盲删未知拉取中完整对象的统一年龄规则。

## 11. 发布门槛与验收

按先后顺序完成以下门槛，不以功能开关绕过未验证能力：

1. 固定 SDK 的 URL 视频上传、video info/search、原生 share、源 preview URL 获取和目标回读契约；离线 transport doubles 验证真实序列化与响应形态。未被证实的字段、过滤或分页语义保持 blocked。
2. 无 R2 原件场景的源→目标分发：当前源/目标权限、不同目标 VID、失权、无链接、歧义、结果未知、分页恢复和封面全链均正确。
3. 成功原件立即清理，清理不影响源视频、目标映射、封面和冻结素材身份；verify/cleanup/新使用者并发、旧代次迟到清理、DELETE 响应丢失和 HEAD 故障有真实 PostgreSQL 竞态与存储替身测试。
4. 源入库成功丢响应仅回查；共享或接力成功丢响应不切换路径、不第二次 POST。已知 ID 在本地事务或 SDK 清理失败后仍有恢复证据。
5. 8/2 GiB 窗口实测：满额不继续签 part URL，多租户公平推进；删除或 abort 未确认不释放；单个超限文件不拖死整个队列。
6. 10,000 与 20,000 文件工程验收，记录实际文件大小分布、各阶段耗时、数据库查询/锁、worker 内存与磁盘、浏览器内存/IndexedDB、队列公平和故障恢复。证明分页、增量计数和资源有界；不得将离线零延迟替身结果写成 TikTok 实际吞吐。
7. 上线前以独立批准的测试配置验证 R2、官方 SDK、真实授权账户和跨账户路径。真实操作另行按具体范围授权；本设计文档不授权任何线上上传、共享或广告写入。
