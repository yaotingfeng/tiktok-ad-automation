# 已核实补建的业务闭环

适用场景：原 AD 创建结果为 UNKNOWN、没有任何已知远端 ID；用户已明确批准并完成独立补建，需要把新对象的核实结果关联回原搭建任务。此入口只读 TikTok，不创建、停用或启用任何广告。

## 导入条件

- 操作者当前具有该租户的管理权限，使用原预览冻结的 BC、连接、绑定代数和授权版本；连接发生变化时不能改选默认连接绕过校验。
- 原 AD 请求摘要必须完整且与原 REQUEST_ARMED 尝试证据一致；原父组须有已确认 ID。原组不能包含已知创建成功的其他 AD。
- 新 AD 与原冻结请求的账户、视频及顺序、身份、文案、链接、CTA 一致；只允许名称、封面、新父组变化。
- 新组与原组的 campaign、Minis、出价、优化事件、地域及其他配置完全一致；只允许名称与开始时间变化。
- 同一个原组只能映射到一个新组，同一新组不能覆盖其他原组；同一新 AD 不能归属多个原步骤，也不能借用已记录的现有对象。

## 内部入口

`app.modules.builds.corrections.import_verified_replacement` 接收已批准的冻结 `AdCreate`、`AdGroupCreate` 意图，新 AD/组 ID、原 AD 步骤 ID 及请求摘要、固定 `request_id`、审计材料引用和不超过 45 秒的截止时间。

补建原始请求可用 `request_compiler.decode_intent` 转成类型化意图；组请求的传输关联 `request_id` 不属于广告配置，解码前单独保存到原始审计材料。审计材料必须保留创建前冻结请求与创建回执，不能只记录最终成功状态。

服务从应用 gateway 读取新 AD、新 Smart+ 组、新组实际状态和旧组实际状态。只有新对象完整 MATCH、实际 ENABLE，且旧组明确 DISABLE，才在同一事务追加 `build_verified_replacement`。任意缺字段、状态未知、不匹配、越权或归属冲突均拒绝导入。调用失败不安排重建；重试原样使用同一 `request_id`。成功后的相同请求只返回原台账 ID。

不允许直接写台账，或把外部 JSON 中的 MATCH/ENABLE 当成平台证据。没有公开的“标记成功”接口。

## 展示与恢复

原 AD 的 UNKNOWN、请求、远端 ID、创建尝试，以及原依赖 READBACK 的失败记录全部保留。业务汇总将已核实替代 AD 计入成功，原组显示其对应新组；计划对象数不增加。全部结果完成时显示“已完成（含 N 条补建）”。原组的停用事实与原尝试结果仍能从明细辨认。

已补建的原 AD/组和相应 READBACK 不再进入一键恢复、自动修复或历史只读核查队列。尚未核实的其他 UNKNOWN 保持需要处理；部分补建不会把整个任务提前标记完成。
